# 文件系统类型与布局重构方案（零行为变更）

> 目标：本方案只改善代码可读性与可维护性，不改变 `.sy` 格式的任何字节，也不改变任何运行行为。
> 与《线程池调研与改造计划.md》相互独立，可以单独执行，先后顺序不限。
> 行号以 2026-09-03 的工作区为准。
>
> 2026-09-03 增补：R1 的常量落点修订（Header::Layout 嵌套）、R4 的 FileTask 细化为双字段、
> 新增 R6/R7（偏移量游标收口到类内嵌套结构）与 CLI 基准验收工具。

## 0. 验收标准（重构完成的判定）

1. 全量构建无警告（`BuildTest/`，Release + 静态 Qt）；
2. test_aes（186 项）、test_bufferpool（22 项）、test_huffman（115 项）、test_flagtype（28 项）全部通过；
3. 最严格的验证：无加密模式（PackOnly / HuffmanOnly）下，重构前后对同一输入分别压缩，生成的归档文件逐字节一致（CLI 基准工具 `tool_archivebaseline` 自动执行 + `fc /B`）；加密模式因为 IV 每次随机生成，无法逐字节对比，以压缩→解压一致性为准；
4. baseline 归档经 CLI 工具解压后与源样本目录树一致（读取侧重构的回归锚点）；
5. GUI 四种策略压缩→解压，输出与源文件一致（可选人工复验）。

CLI 基准工具说明：仿 test_flagtype 模式的独立可执行文件（`BuildTest/tests/tool_archivebaseline.cpp`），
程序内生成固定样本树（多级目录 + 中文名，不含需特权的符号链接），直接编译仓库源文件并调用
`CompressionLoop` / `DecompressionLoop`，提供 compress / decompress / verify 三个子命令。

## 1. 现状

### 1.1 类型别名与其实际用途（`FileLibrary.h:14-35`）

| 类型 | 名义用途 | 实际用途 | 问题程度 |
|---|---|---|---|
| `FileNameSize` (u32) | 文件名长度 | 文件名长度；还被用作回写位置在归档中的偏移（`CompressionLoop.cpp:85` 的 `offsetToFill`） | 高：名称与实际用途不符 |
| `DirectoryOffsetSize` (u64) | 目录偏移 | 文件头的 `directoryOffset` 字段；目录扫描用的 `tempOffset`/`offset` 两个偏移变量；数据块长度字段（`DataExporter` 回写的内容）；`blockPosition` 记录 | 高：一个类型承担四种用途 |
| `FileSize` (u64) | 文件大小 | 源文件大小；`DataExporter` 的 `processedFileSize`（回写值） | 中：两种用途都表示字节数，尚可接受 |
| `IvSize` = `array<uint8_t,16>` | — | IV 的值类型；同时 `sizeof(IvSize)` 又参与位置计算 | 中：名称含 Size 却是一个值类型 |
| `SizeOfMagicNum` / `SizeOfFlag` | 字段宽度 | 字段类型 | 低：命名含糊，但改名影响范围大，本方案不处理 |
| `UpSizeOfBuffer` / `ConstSize` / `MetadataMarker` | — | — | 低，可改可不改 |

### 1.2 分散在各处的布局计算（六处）

| 位置 | 表达式 | 含义 |
|---|---|---|
| `HeaderWriter.cpp:26` | `HEADER_SIZE - sizeof(MAGIC) - sizeof(DirectoryOffsetSize) - sizeof(HeaderOffsetSize)` | 计算文件头内 `headerOffset` 预留字段的位置 |
| `HeaderWriter.cpp:46` | `HEADER_SIZE - sizeof(MAGIC) - sizeof(DirectoryOffsetSize)` | 计算文件头内 `directoryOffset` 预留字段的位置 |
| `HeaderWriter.cpp:47` | `directoryOffset + sizeof(MAGIC)` | 补偿结尾魔数此时尚未写入 |
| `DataExporter.cpp:8` | `currentPos - (dataSize + sizeof(DirectoryOffsetSize))` | 通过 `tellp` 反向计算块长度字段的位置 |
| `BinaryStandardLoader.cpp`（encryptHeaderBlock） | `startPos - sizeof(IvSize)` | 定位目录块前的 IV 预留空间 |
| `FileLibrary.h:81-85` 的长注释 | — | 解释为什么不使用文件流返回的位置、而由程序手动维护偏移 |

已有的基础：`SEPARATED_STANDARD_SIZE` 等布局常量已经集中在 `Constants` 中；问题在于各处计算预留字段位置的表达式没有同样集中，仍在使用处现场推算。

### 1.3 目录信息的存储形式与回写位置的产生过程

目录信息以**树结构**序列化存储：逻辑根节点记录子项数量，每个目录节点记录各自的子项数量，文件条目跟随其所属目录节点，整体按广度优先顺序写出（`EntryProcessor.cpp` 的 `flowScanner` 循环）。压缩时的流程：

1. `EntryProcessor` 与 `BinaryStandardWriter` 写目录，用 `tempOffset` 和 `offset` 两个偏移变量手动维护各条目在归档中的位置；每个文件条目中预留一个表示"处理后大小"的字段；
2. 压缩数据写完后，`BinaryStandardLoader` 重新读取目录建立 `fileQueue`，队列每个元素的 second 记录该文件预留字段在归档中的偏移；
3. `CompressionLoop` 在该文件全部数据写完后取出该偏移，调用 `thisFileIsDone` 把实际大小写回预留字段。

## 2. 重构内容（按执行顺序）

### R1 新增布局派生常量（只新增代码，不修改现有语句）

落点修订（2026-09-03）：文件头内两个预留字段的位置只与 `Header` 布局相关，
嵌套为 `Header::Layout` 而不是散进 `Constants` 大命名空间；跨区块的宽度常量仍放 `Constants`：

```cpp
// FileLibrary.h — Header 内部布局的位置派生常量（相对文件头起点，按字段顺序累积，
// 不依赖在 Header 之后才定义的 Constants::HEADER_SIZE）
struct Header {
    // ... 现有字段 ...
    struct Layout {
        static constexpr ConstSize HEADER_OFFSET_FIELD_POS =
            sizeof(SizeOfMagicNum) + sizeof(CompressStrategy) + sizeof(CompressorVersion); // = 6
        static constexpr ConstSize DIRECTORY_OFFSET_FIELD_POS =
            HEADER_OFFSET_FIELD_POS + sizeof(HeaderOffsetSize); // = 7
    };
};
// Constants 定义之后交叉验证：累积形式与 sizeof(Header) 一致
static_assert(Header::Layout::DIRECTORY_OFFSET_FIELD_POS + sizeof(DirectoryOffsetSize) +
              sizeof(SizeOfMagicNum) == Constants::HEADER_SIZE);

// Constants 内 — 跨区块的宽度常量
constexpr ConstSize BLOCK_LENGTH_FIELD_SIZE = sizeof(DirectoryOffsetSize); // 数据块前缀中"块长度字段"的宽度
constexpr ConstSize IV_BYTES = 16;   // 供位置计算使用；IvSize 是值类型，位置计算不应依赖 sizeof(值类型)
```

然后把 §1.2 表中各处表达式改为引用这些常量。每个替换都是用常量代替同一表达式，行为不变。

### R2 类型改名（机械替换）

原则：**偏移和长度使用不同的类型名称**。新增类型别名：

```cpp
using SlotOffset = uint64_t;   // 预留字段在归档中的偏移
using BlockLength = uint64_t;  // 数据块长度
```

- `FileNameSize` 用作偏移的场合改为 `SlotOffset`：`CompressionLoop.cpp:85`、`fileQueue` 元素的第二个类型、生产与消费两侧（`EntryParser` / `BinaryStandardLoader` / `DecompressionLoop` 对应位置）；
- `DirectoryOffsetSize` 用作块长度的场合改为 `BlockLength`：`thisBlockIsDone` / `thisFileIsDone` 的参数、`exportCompressedData` 的局部变量；
- `FileNameSize`（文件名长度）与 `DirectoryOffsetSize`（目录偏移、扫描游标）的正当用途保留不动。

每改一组：`git grep` 确认目标用法全部替换、没有遗漏 → 构建 → 做一次完整提交。注意 `FileNameSize` 的替换需要逐处判断该处语义是"长度"还是"偏移"，不能全局盲目替换。

### R3 布局结构体与 static_assert（只定义，不改变写入方式）

```cpp
#pragma pack(push, 1)
struct SeparatedPrefix { FlagType flag; BlockLength length; IvSize iv; }; // 磁盘顺序 flag+块长+IV
struct FileStandardTail { FileSize originalSize; FileSize processedSize; };
#pragma pack(pop)
static_assert(sizeof(SeparatedPrefix) == SEPARATED_STANDARD_SIZE);
static_assert(sizeof(FileStandardTail) == sizeof(FileSize) * 2);
```

（2026-09-03 修正：初版此处的 `SeparatedPrefix` 字段顺序误写为 flag+iv+length，
与 `writeBlankSeparatedStandard` / `loadSeparatedStandard` 的实际读写顺序
flag+length+iv 不符，已按实际磁盘布局更正。）

边界（重要）：结构体在本方案中只作为布局的唯一定义和编译期校验，**写入路径仍然按现有方式逐字段调用 `writeBinaryStandards`**，不改为一次性写入整个结构体，避免引入字节顺序或填充方面的差异。是否改为整体写入留待将来的格式版本再决定。

### R4 fileQueue 改用具名结构

`std::queue<std::pair<EntryDetails, Y_flib::FileNameSize>>` 改为（2026-09-03 细化：双字段，
显式区分两种模式各自的载荷，消灭 pair.second 双语义——即 `BinaryStandardLoader.h` TODO 清单第 4 条）：

```cpp
struct FileTask {
    EntryDetails entry;              // 待处理文件的目录条目
    SlotOffset  processedSizeOffset; // 压缩模式：该文件"处理后大小"预留字段在归档中的偏移
    FileSize    compressedSize;      // 解压模式：该文件压缩后的大小
};
using FileTaskQueue = std::queue<FileTask>;
```

涉及位置：`ToolClasses.h` 的 `EntryQueue` 定义（fileQueue 换用 `FileTaskQueue`；entryQueue 的
second 语义单一（子项数），本方案不改）、`CompressionLoop` / `DecompressionLoop` 的使用处、
`EntryParser` / `BinaryStandardLoader` 的生产处。纯类型替换，行为不变。

### R5 输出文件的三阶段写入说明

在 `HeaderWriter.h` / `DataExporter.h` / `BinaryStandardLoader.h` 三处类定义的注释中加入同一段说明：

> 归档输出文件的写入分三个阶段依次进行，任何阶段都不并发写入：
> ① HeaderWriter（ofstream，建档阶段：写文件头、目录树、各预留字段）
> ② DataExporter（fstream，数据阶段：逐块追加，并回写每块长度、每文件大小）
> ③ BinaryStandardLoader::encryptHeaderBlock（fstreamForRefill，收尾阶段：目录区原地加密）
> 并行化时②③归专职写线程，见《线程池调研与改造计划.md》§7.1。

## 2A. 偏移量游标收口到类内嵌套结构（R6/R7，2026-09-03 增补）

R1-R4 只语义化"类型与常量"，不动"维护逻辑的分布"。R6/R7 更进一步：把两侧游标的状态
与其维护不变式（累加、阈值分割、回填定位、剩余量扣减、位置推导）收口为**类内嵌套结构**，
散落在 6 个文件的裸算术全部改走游标方法。

### R6 写入侧：`BinaryStandardWriter::DirectoryScanCursor`

现状：`tempOffset`（当前块累计标准字节）与 `offset`（下一个分割标准 flag 的绝对位置）诞生于
`EntryProcessor.cpp:20-21`，以 `DirectoryOffsetSize&` 裸引用穿透 `BinaryStandardWriter` 的 8 个方法；
`tempOffset +=` 出现在 4 个写入函数内；分割/回填逻辑（`writeStorageStandard` 的阈值分支 +
`writeSeparatedStandard` 的 `offset + FLAG_SIZE` 定位）内联在函数体里。

设计（public 嵌套，EntryProcessor 需要构造并传递它）：

```cpp
struct DirectoryScanCursor {
    // 下一个分割标准 flag 字节的绝对偏移（原 offset），初值即第一个空分割标准的位置
    SlotOffset nextSlotPos = Constants::HEADER_SIZE;
    // 当前块自分割标准之后累计的标准字节数（原 tempOffset）
    BlockLength blockBytes = 0;

    void accountEntry(BlockLength standardSize) { blockBytes += standardSize; } // 原 tempOffset += ...
    bool needsSeparation() const { return blockBytes >= Constants::HEADER_BUFFER_SIZE; }
    SlotOffset lengthSlotPos() const { return nextSlotPos + Constants::FLAG_SIZE; } // 块长度槽位（跳过 flag）
    void onBlockSealed()  { nextSlotPos += blockBytes; blockBytes = 0; }  // 回填后：块闭合，游标跳过块体
    void onSlotReserved() { nextSlotPos += Constants::SEPARATED_STANDARD_SIZE; } // 预写空槽后：跳过槽位
};
// 不变式（继承原设计）：blockBytes 不含分割标准自身大小——nextSlotPos 永远指向
// "拿到即可直接定位"的槽位 flag，无需二次变换。
```

职责边界：**游标只做位置算术，字节写入留在 Writer**。`writeStorageStandard` 的分割分支变为
`writeSeparatedStandard(cursor); cursor.onBlockSealed(); writeBlankSeparatedStandard(); cursor.onSlotReserved();`
8 个方法签名从 `(tempOffset&, offset&)` 收敛为 `(DirectoryScanCursor&)`；
`EntryProcessor.cpp:20-21` 的手工初始化消失（默认成员初值即正确起点）。

### R7 读取侧：`DirectoryReadCursor`（独立头 + Loader 内嵌套别名）

现状：`offset`（目录区剩余未读字节数）与 `tempOffset`（当前块长，0=末块）是
`BinaryStandardLoader` 成员，被 `EntryParser` 以 const 引用跨类绑定共享；
`directoryOffset - offset` 推导出现 3 处（Loader.cpp:12 / 241、EntryParser.cpp:51 变体）；
`blockPosition` 用裸 `array<u64,2>` 冒充 {起点,大小}。

物理位置：新头 `ArchiveFormat/include/DirectoryCursor.h`（`EntryParser.h` 与
`BinaryStandardLoader.h` 都要引用游标类型，若嵌套定义在 Loader 类内会造成循环包含；
独立物理定义 + Loader 内 `using ReadCursor = DirectoryReadCursor;` 保持"类内"语义归属）。

```cpp
struct DirectoryReadCursor {
    BlockLength remaining = 0; // 目录区剩余未读字节数（原 Loader 侧 offset）
    BlockLength blockLen = 0;  // 当前块长度（原 Loader 侧 tempOffset；0 表示最后一块）

    void initFromHeader(SlotOffset dataAreaStart) { remaining = dataAreaStart - Constants::HEADER_SIZE; }
    SlotOffset nextReadPos(SlotOffset dataAreaStart) const { return dataAreaStart - remaining; } // 收口 3 处推导
    bool onlyMagicRemains() const { return remaining == sizeof(SizeOfMagicNum); }
    bool hasData() const { return remaining > 0; }
    bool isLastBlock() const { return blockLen == 0; }
    BlockLength bytesInThisBlock() const // 末块（分割标准长度槽为 0）剩余量去掉结尾魔数
        { return isLastBlock() ? remaining - sizeof(SizeOfMagicNum) : blockLen; }
    void consumeSeparated(BlockLength len) // 读出一个分割标准后：跳过槽位与块体
        { remaining -= Constants::SEPARATED_STANDARD_SIZE + len; blockLen = len; }
    void consumeFinalBlock(BlockLength readSize) { remaining -= readSize; } // 末块读完后
    SlotOffset entryFieldPos(SlotOffset dataAreaStart, BlockLength bufferPtr) const // 原 EntryParser.cpp:51
        { return dataAreaStart - (remaining + blockLen) + bufferPtr; } // 推导：目录区当前位置-块长回块首+块内游标
    bool blockEndReached(BlockLength bufferPtr) const // 原 EntryParser.cpp:144
        { return blockLen != 0 && blockLen <= bufferPtr; }
};
```

同步改造：
- Loader 的 `offset`/`tempOffset` 成员删除，换 `DirectoryReadCursor cursor;`；9 处用法
  （定位、末魔数判定、主循环条件、readSize 三元、末块扣减、header 初始化、分割标准扣减、
  restart 定位、EntryParser 构造传参）逐一改游标方法；
- `EntryParser` 的两个 const 引用成员收敛为 `const DirectoryReadCursor &cursor`；
  `EntryParser.cpp:51` 的最复杂偏移公式收口为 `cursor.entryFieldPos(header.directoryOffset, bufferPtr)`；
- Loader 内新增嵌套 `struct BlockSpan { SlotOffset startPos; BlockLength size;
  SlotOffset ivSlotPos() const { return startPos - Constants::IV_BYTES; } }`，
  `blockPosition` 改为 `std::vector<BlockSpan>`，`encryptHeaderBlock` 的 `startPos - sizeof(IvSize)`
  布局知识随之收口。

约束：每个方法的实现与原语句逐句对应（特别是末块 `isLastBlock` 提前 return 分支的扣减时序），
方法处保留不变式注释。

## 3. 执行顺序与总验收

R1（新增常量）→ R2（类型改名，分组提交）→ R3 + R4 → **CLI 基准工具生成 baseline** →
R6（写入侧嵌套游标）→ R7（读取侧嵌套游标）→ R5（注释）→ §0 五条验收全部通过 → 最终提交。

R6/R7 每步完成后立即用 CLI 工具做 PackOnly/HuffmanOnly 逐字节对比 + baseline 解压往返，
任何一步不一致就地修复，不带病前进。

工作量估计：R1-R4 约 2-4 小时（R2 的替换范围比看起来大，`FileNameSize` 需要逐处确认语义）；
R6/R7 约 3-4 小时；CLI 基准工具约 1 小时。

## 4. 明确不做的事

- 不改变任何写入归档的字节：不调整对齐、不整体写入结构体、不调整字段顺序；
- 不修改加密模块及其类型；
- 不做目录后置、尾部索引之类的格式重新设计（那是另一个方向的将来选项）；
- 不简化任何写入顺序逻辑——本方案唯一目的是让现有的正确实现变得可读、可查，并为并发改造做好准备。
