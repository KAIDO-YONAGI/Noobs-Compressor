# 文件系统类型与布局重构方案（零行为变更）

> 目标：本方案只改善代码可读性与可维护性，不改变 `.sy` 格式的任何字节，也不改变任何运行行为。
> 与《线程池调研与改造计划.md》相互独立，可以单独执行，先后顺序不限。
> 行号以 2026-09-03 的工作区为准。

## 0. 验收标准（重构完成的判定）

## 1. 现状

### 1.1 类型别名与其实际用途（`FileLibrary.h:14-35`）

| 类型 | 名义用途 | 实际用途 | 问题程度 |
|---|---|---|---|
| `FileNameSize` (u32) | 文件名长度 | 文件名长度；还被用作回写位置在归档中的偏移（`CompressionLoop.cpp:85` 的 `offsetToFill`） | 高：名称与实际用途不符 |
| `DirectoryOffsetSize` (u64) | 目录偏移 | 文件头的 `directoryOffset` 字段；目录扫描用的 `tempOffset`/`offset` 两个偏移变量；数据块长度字段（`DataExporter` 回写的内容）；`blockPosition` 记录 | 高：一个类型承担四种用途 |
| `FileSize` (u64) | 文件大小 | 源文件大小；`DataExporter` 的 `processedFileSize`（回写值） | 中：两种用途都表示字节数，尚可接受 |
| `IvSize` = `array<uint8_t,16>` | — | IV 的值类型；同时 `sizeof(IvSize)` 又参与位置计算 | 中：名称含 Size 却是一个值类型 |
| `SizeOfMagicNum` / `SizeOfFlag` | 字段宽度 | 字段类型 | 低：命名含糊，但改名影响范围大，本方案不处理 |
| `UpSizeOfBuffer` / `ConstSize` / `MetadataMarker` | — | — | 低，可改可不改 |

### 1.2 分散在各处的布局计算（六处）

| 位置 | 表达式 | 含义 |
|---|---|---|
| `HeaderWriter.cpp:26` | `HEADER_SIZE - sizeof(MAGIC) - sizeof(DirectoryOffsetSize) - sizeof(HeaderOffsetSize)` | 计算文件头内 `headerOffset` 预留字段的位置 |
| `HeaderWriter.cpp:46` | `HEADER_SIZE - sizeof(MAGIC) - sizeof(DirectoryOffsetSize)` | 计算文件头内 `directoryOffset` 预留字段的位置 |
| `HeaderWriter.cpp:47` | `directoryOffset + sizeof(MAGIC)` | 补偿结尾魔数此时尚未写入 |
| `DataExporter.cpp:8` | `currentPos - (dataSize + sizeof(DirectoryOffsetSize))` | 通过 `tellp` 反向计算块长度字段的位置 |
| `BinaryStandardLoader.cpp`（encryptHeaderBlock） | `startPos - sizeof(IvSize)` | 定位目录块前的 IV 预留空间 |
| `FileLibrary.h:81-85` 的长注释 | — | 解释为什么不使用文件流返回的位置、而由程序手动维护偏移 |

已有的基础：`SEPARATED_STANDARD_SIZE` 等布局常量已经集中在 `Constants` 中；问题在于各处计算预留字段位置的表达式没有同样集中，仍在使用处现场推算。

### 1.3 目录信息的存储形式与回写位置的产生过程

目录信息以**树结构**序列化存储：逻辑根节点记录子项数量，每个目录节点记录各自的子项数量，文件条目跟随其所属目录节点，整体按广度优先顺序写出（`EntryProcessor.cpp` 的 `flowScanner` 循环）。压缩时的流程：

1. `EntryProcessor` 与 `BinaryStandardWriter` 写目录，用 `tempOffset` 和 `offset` 两个偏移变量手动维护各条目在归档中的位置；每个文件条目中预留一个表示"处理后大小"的字段；
2. 压缩数据写完后，`BinaryStandardLoader` 重新读取目录建立 `fileQueue`，队列每个元素的 second 记录该文件预留字段在归档中的偏移；
3. `CompressionLoop` 在该文件全部数据写完后取出该偏移，调用 `thisFileIsDone` 把实际大小写回预留字段。

## 2. 重构内容（按执行顺序）

### R1 新增布局派生常量（只新增代码，不修改现有语句）

在 `Constants` 内新增由布局推导的位置常量：

```cpp
// 文件头内两个预留字段的位置（相对文件头起点；字段构成见 Header 结构体）
constexpr ConstSize HEADER_OFFSET_FIELD_POS =
    HEADER_SIZE - sizeof(SizeOfMagicNum) - sizeof(DirectoryOffsetSize) - sizeof(HeaderOffsetSize);
constexpr ConstSize DIRECTORY_OFFSET_FIELD_POS =
    HEADER_SIZE - sizeof(SizeOfMagicNum) - sizeof(DirectoryOffsetSize);
// 数据块前缀中"块长度字段"的宽度
constexpr ConstSize BLOCK_LENGTH_FIELD_SIZE = sizeof(DirectoryOffsetSize);
constexpr ConstSize IV_BYTES = 16;   // 供位置计算使用；IvSize 是值类型，位置计算不应依赖 sizeof(值类型)
```

然后把 §1.2 表中各处表达式改为引用这些常量。每个替换都是用常量代替同一表达式，行为不变。

### R2 类型改名（机械替换）

原则：**偏移和长度使用不同的类型名称**。新增类型别名：

```cpp
using SlotOffset = uint64_t;   // 预留字段在归档中的偏移
using BlockLength = uint64_t;  // 数据块长度
```

- `FileNameSize` 用作偏移的场合改为 `SlotOffset`：`CompressionLoop.cpp:85`、`fileQueue` 元素的第二个类型、生产与消费两侧（`EntryParser` / `BinaryStandardLoader` / `DecompressionLoop` 对应位置）；
- `DirectoryOffsetSize` 用作块长度的场合改为 `BlockLength`：`thisBlockIsDone` / `thisFileIsDone` 的参数、`exportCompressedData` 的局部变量；
- `FileNameSize`（文件名长度）与 `DirectoryOffsetSize`（目录偏移、扫描游标）的正当用途保留不动。

每改一组：`git grep` 确认目标用法全部替换、没有遗漏 → 构建 → 做一次完整提交。注意 `FileNameSize` 的替换需要逐处判断该处语义是"长度"还是"偏移"，不能全局盲目替换。

### R3 布局结构体与 static_assert（只定义，不改变写入方式）

```cpp
#pragma pack(push, 1)
struct SeparatedPrefix { FlagType flag; IvSize iv; BlockLength length; };
struct FileStandardTail { FileSize originalSize; FileSize processedSize; };
#pragma pack(pop)
static_assert(sizeof(SeparatedPrefix) == SEPARATED_STANDARD_SIZE);
static_assert(sizeof(FileStandardTail) == sizeof(FileSize) * 2);
```

边界（重要）：结构体在本方案中只作为布局的唯一定义和编译期校验，**写入路径仍然按现有方式逐字段调用 `writeBinaryStandards`**，不改为一次性写入整个结构体，避免引入字节顺序或填充方面的差异。是否改为整体写入留待将来的格式版本再决定。

### R4 fileQueue 改用具名结构

`std::queue<std::pair<EntryDetails, Y_flib::FileNameSize>>` 改为：

```cpp
struct FileTask {
    EntryDetails entry;              // 待处理文件的目录条目
    SlotOffset  processedSizeOffset; // 该文件"处理后大小"预留字段在归档中的偏移
};
using FileTaskQueue = std::queue<FileTask>;
```

涉及位置：`ToolClasses.h` 的 `EntryQueue` 定义、`CompressionLoop` / `DecompressionLoop` 的使用处、`EntryParser` / `BinaryStandardLoader` 的生产处。纯类型替换，行为不变。

### R5 输出文件的三阶段写入说明

在 `HeaderWriter.h` / `DataExporter.h` / `BinaryStandardLoader.h` 三处类定义的注释中加入同一段说明：

> 归档输出文件的写入分三个阶段依次进行，任何阶段都不并发写入：
> ① HeaderWriter（ofstream，建档阶段：写文件头、目录树、各预留字段）
> ② DataExporter（fstream，数据阶段：逐块追加，并回写每块长度、每文件大小）
> ③ BinaryStandardLoader::encryptHeaderBlock（fstreamForRefill，收尾阶段：目录区原地加密）
> 并行化时②③归专职写线程，见《线程池调研与改造计划.md》§7.1。

## 3. 执行顺序与总验收

R1（新增常量）→ R2（类型改名，分组提交）→ R3 + R4 → R5（注释）→ §0 四条验收全部通过 → 最终提交。

工作量估计：一次完成约 2-4 小时。R2 的替换范围比看起来大，`FileNameSize` 需要逐处确认语义。

## 4. 明确不做的事

- 不改变任何写入归档的字节：不调整对齐、不整体写入结构体、不调整字段顺序；
- 不修改加密模块及其类型；
- 不做目录后置、尾部索引之类的格式重新设计（那是另一个方向的将来选项）；
- 不简化任何写入顺序逻辑——本方案唯一目的是让现有的正确实现变得可读、可查，并为并发改造做好准备。
