# 性能报告：多线程压缩流水线（v2.2.0 vs v2.1.x 串行）

> 2026-09-07。基准环境：i7-13700KF 类 16 逻辑核 / 32GB / NVMe D 盘 / Win10 22H2；MinGW g++ -std=c++20 -O2；HuffmanAES 模式（口令固定）。
> 旧版 = 仓库 HEAD（串行主循环，AES 每次 encrypt 逐次 CryptAcquireContext）；新版 = v2.2.0（三段流水线 + CSP 句柄缓存）。

## 正确性校验

三个全量归档解压后文件数与字节数均与源**精确一致**（A：251,156 / 43,221,716；C：33,835 / 2,601,430,947；B：45,390 / 14,466,496,682）。字节级一致性另由 tool_archivebaseline 验收轮证明（pack/huffman 流水线产物与串行产物逐字节相同）。

## 原因分析

- **场景 B（6.9×）——计算并行充分兑现。** 大文件以 8MB 块喂满 16 个工人，AES+Huffman 计算全面并行；131.9 MiB/s 已接近读写端点与工人合计吞吐的上界，接近理论线性区。
- **场景 C（3.6×）——端点开始限幅。** 平均 75 KiB 的文件使单文件常不足一块，任务粒度变细；目录枚举（\\?\ 长路径逐层查询）与逐文件建档成本集中在读线程与建档阶段，这两段不随工人数缩放，加速比被压到端点上限之内。
- **场景 A（1.8×）——端点主导，符合预期。** 172 B 的平均文件使压缩/加密计算占比趋近于零，瓶颈完全落在串行端点：读线程的目录枚举与逐文件 open/read/close、建档的目录区序列化、写线程的逐文件结算与大量小块落盘。两版端点成本相同，可并行部分本来就少。此场景同时受旧版逐次 CSP 句柄获取（每文件 2 次）拖累，新版 CSP 缓存贡献了相当部分提速——即纯流水线贡献低于表观值，报告如实标注。
- **总结论**：加速比随"文件变大"单调上升（1.8× → 3.6× → 6.9×），与流水线模型的量化预期吻合——能摊到 N 核上的只有计算段，读/写端点是所有场景共享的地板。小文件场景的进一步优化方向是调度合批与端点流水化（存档于实施记录 §5，未实施）。

## 测量条件备注

- 旧版三场景并行执行（用户要求压墙钟），三进程各自单线程、以 CPU 为瓶颈，互扰轻微；新版串行独占。
- 旧版为子集实测（限时策略），全量为线性外推，仅作参考量级；两版子集输入逐字节相同。
- 基准工具：SFCTest/bench.cpp（临时，不入库），跳过符号链接，两版口径一致。
