# 性能报告：多线程压缩流水线（v2.2.0 vs v2.1.x 串行）

> 2026-09-07。基准环境：16 逻辑核 / 32GB / NVMe D 盘 / Win10 22H2；MinGW g++ -std=c++20 -O2；HuffmanAES 模式（口令固定）。
> 旧版 = 仓库上一提交（串行主循环，AES 每次 encrypt 逐次 CryptAcquireContext）；新版 = v2.2.0（三段流水线 + CSP 句柄缓存）。
> 本文以**吞吐量**（单位时间处理的数据量/文件数）为主要刻度——速度是除法，秒数只是单次事件的注脚，附在附录供复现。

## 1. 压缩吞吐对照（同机、同输入、同模式）

| 场景 | 数据特征 | 旧版吞吐 | 新版吞吐 | 提升 |
|---|---|---|---|---|
| B 正常文件 | 均 311KB/文件，4GiB 子集 | 19.1 MiB/s | **131.9 MiB/s** | **6.9×** |
| C 长路径 | 均 75KB/文件，2.42GiB 全量，路径最深 267 字符 | 14.7 MiB/s | **52.6 MiB/s** | **3.6×** |
| A 小文件极端 | 均 172B/文件，15 万文件子集 | 962 文件/s | **1,743 文件/s** | **1.8×** |

另一个倒数视角——**每压缩 1 GiB 的耗时**：

| 场景 | 旧版 | 新版 |
|---|---|---|
| B 正常文件 | 53.6 s/GiB | **7.8 s/GiB** |
| C 长路径 | 69.6 s/GiB | **19.5 s/GiB** |

新版全量成绩（无子集截取）：

| 场景 | 全量规模 | 新版吞吐 |
|---|---|---|
| B 正常文件 | 13.47GiB / 45,390 文件 | 106.5 MiB/s（每 GiB 9.6 秒） |
| C 长路径 | 2.42GiB / 33,835 文件 | 52.6 MiB/s |
| A 小文件极端 | 41.2MiB / 251,156 文件 | 1,518 文件/s |

旧版全量为按子集吞吐线性外推（量级参考）：B ≈ 19.1 MiB/s（全量约 12 分钟），A ≈ 962 文件/s（全量约 4.4 分钟）。

## 2. 解压吞吐（两版同码，仍串行）

| 场景 | 解压吞吐 |
|---|---|
| A 小文件极端 | 1,135 文件/s |
| B 正常文件（全量 13.47GiB） | 24.1 MiB/s |
| C 长路径（全量 2.42GiB） | 19.7 MiB/s |

解压是当前最明显的待优化项（见 §5）。

## 3. 正确性校验

三个全量归档解压后文件数与字节数均与源**精确一致**（A：251,156 / 43,221,716；B：45,390 / 14,466,496,682；C：33,835 / 2,601,430,947）。字节级一致性另由 tool_archivebaseline 验收轮证明（pack/huffman 流水线产物与串行产物逐字节相同）。

## 4. 原因分析

- **场景 B（6.9×）——计算并行充分兑现。** 大文件以 8MB 块喂满 16 个工人，AES+Huffman 计算全面并行；131.9 MiB/s 已逼近读写端点与工人合计吞吐的上界。
- **场景 C（3.6×）——端点开始限幅。** 平均 75KB 的文件使单文件常不足一块，任务粒度变细；目录枚举（\\?\ 长路径逐层查询）与逐文件建档成本集中在读线程与建档阶段，这两段不随工人数缩放。
- **场景 A（1.8×）——端点主导，符合设计预期。** 172B 的平均文件使计算占比趋近于零，瓶颈完全落在串行端点：读线程的枚举与逐文件 open/read/close、建档的目录区序列化、写线程的逐文件结算与小块落盘。两版端点成本相同，可并行部分本来就少。此场景同时受旧版逐次 CSP 句柄获取（每文件 2 次）拖累，新版 CSP 缓存贡献了相当部分提速——即纯流水线贡献低于表观值，如实标注。
- **总结论**：吞吐提升随"文件变大"单调放大（1.8× → 3.6× → 6.9×），与流水线模型预期吻合——能摊到 N 核上的只有计算段，读/写端点是所有场景共享的地板。

## 5. 后续优化方向（本期未实施）

- **解压并行化**（20~24 MiB/s → 目标对齐压缩侧收益，优先级最高）；
- **小文件场景端点优化**：调度合批（读侧突发入队、工人按字节预算批量取）、读线程枚举与建档流水化；
- ThreadSanitizer 数据竞争检查。

## 6. 方法与测量条件

- 子集口径：旧版限时 ≤5 分钟——先以 ~30 秒切片标定吞吐，再反推"≤4 分钟"对应数据量，按确定顺序从场景树截取；新旧两版压缩**逐字节相同**的子集。场景 C 的预算盖住全量，即全量对照。
- 旧版三场景三进程并行执行（各自单线程，互扰轻微）；新版独占机器串行执行。
- 旧版全量数字为线性外推，仅作量级参考。
- 基准工具为一次性程序（不入库）：确定顺序遍历、跳过符号链接、GBK→UTF-8 参数清洗，两版口径一致。
