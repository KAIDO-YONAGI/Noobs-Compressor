## 1. 现状：已经有什么

压缩路径目前是单线程串行，但职责已经拆干净，多线程要接的缝都在。

写入三阶段（已落地，零字节验收通过）：

| 阶段 | 类 | 职责 |
|---|---|---|
| 建档 | HeaderWriter | 创建归档，写文件头、目录树、各预留字段 |
| 数据 | DataExporter | 纯追加：分隔标志 + 真实块长 + 数据，从不 seek 回改 |
| 收尾 | CatalogFinalizer | 先回填各文件"处理后大小"槽，再目录区原地加密，次序焊死在类内 |

串行总指挥 CompressionLoop 的编排（现行代码）：

- 目录驱动装载：BinaryStandardLoader 迭代目录区得到文件队列，逐文件 DataLoader 读块（`CompressionLoop.cpp:40-66`）；
- 每块处理：compress 产元数据 + 数据两段，各自 encrypt，各自连续写盘（`:80-85`）；
- 文件完成：槽偏移 + `DataExporter::currentFileProcessedSize()` 当场配对记进 `sizeFillEntries` 表，然后 `startNextFile()`（`:97-101`）；
- 全部完成：`CatalogFinalizer::finalize(sizeFillEntries, loader.takeBlockSpans(), encryption, mode)`（`:125-127`）。

其他：

- BinaryStandardLoader 是纯读类，读目录时顺手记目录块位置，`takeBlockSpans()` 移交；
- 文件队列元素 FileTask 带具名字段 `processedSizeOffset`（压缩侧槽偏移）；
- BufferPool 已实现、有单测：`acquire` 池空阻塞（背压点），`release` 清长度留容量，`close` 后 `acquire` 抛异常；
- `ThreadPool/` 是空目录，白纸；
- GUI 侧 CompressionWorker 组装模块后调 `compressionLoop`（`CompressionWorker.cpp:204、:247`）。停止标志是原子量，进度信号参数全为 Qt 内建类型，跨线程排队连接安全。

上一轮验收存档（2026-09-06）：pack/huffman 与拆分前逐字节一致；roundtrip 711 文件 × 2 模式；AES 带密码端到端 712 文件全对。

## 2. 目标架构

```
专职读线程 ──任务队列──> 计算池（N 个工人）──结果队列──> 专职写线程
      │                                                    │
      └──────────── 全局 BufferPool（在途大块上限）──────────┘
```

为什么是两条专职线程加一个池：文件流、目录迭代、输出顺序、写盘位置都是不可共享的顺序状态，归专职线程；计算无跨任务状态（模块状态按线程私有，见 §3.3），进共享池并行。读、写若做成池任务会在池内互相等待，造成池内饥饿。

任务粒度与消息协议，按现行代码钉死。一个任务 = 一个 8MB 输入块；串行版每块产两段输出（加密元数据块 + 加密数据块），流水线原样沿用：

```
任务     : { 文件标识, 块序号, 输入块（池借出） }
任务结果 : { 文件标识, 块序号, 元数据块（KB 级，不进池）, 数据块（池借出） }
```

写线程按序号重组后，仍按"元数据块紧邻数据块"写出，归档字节布局与串行版完全一致。

内存上界：8MB 级大块只经 BufferPool 以移动语义流通——读线程借 → 随任务交给工人 → 工人归还输入块、借输出块 → 写线程写完归还。在途大块总数 = 池容量，与队列长度无关。容量取 `2 × (N + 2)`：最坏情形每个工人同时持一块输入并借一块输出。

背压只有一条路：读线程借不到块就阻塞在池上，下游的慢自动拖住上游。两级队列里流动的是闭包和小对象，不设容量上限。

## 3. 要造的三个组件（ThreadPool/ 从零开始）

### 3.1 管程队列，建两个实例

任务队列（读线程放、工人取）和结果队列（工人放、写线程取）用同一类型。结果队列取出侧虽是单消费者，放入侧仍多工人并发，仍需互斥，不为它另造类型。

四条铁律：

1. 等待谓词用析取：「非空 **或** 已关闭」；
2. 退出判据用合取：「空 **且** 已关闭」——只看关闭会丢任务，只看空会永远等；
3. 关闭：锁内置 closed，然后**唤醒全部**——只唤醒一个，其余睡眠者会永久挂睡；
4. 关闭后放入必须拒绝（API 返回失败），和调用顺序一起构成"关闭后不入队"的双重保证。

类名定稿 `Y_LightLockQueue` 不符合命名规范，落码时改名（如 `BlockingTaskQueue`）。

### 3.2 线程池 v2

接口：`submit` 提交闭包并返回可等待结果；`waitIdle` 等队列空且无任务在跑；`resize` 增减工人；析构先排空再收线程。

要点：

- 工人常驻，任务在锁外执行，锁内只做取闭包和计数；
- 异常封装进结果对象（`packaged_task` 共享指针包装），不在工人栈上裸抛，由提交方或写线程统一重抛；
- `waitIdle` 用独立的运行计数实现，与队列 closed 是两回事（还会不会来任务 vs 干完没有）；
- 缩容：被回收的工人单独置退出标记并唤醒全部；
- 析构 drain：已提交任务全部完成才回收线程，与关闭路径行为一致，需单独测试。

### 3.3 WorkerEnv（每线程模块箱）

AES 的密钥扩展表、哈夫曼的频率表和树根是模块的可变成员状态，共享不安全。给每个工人一份惰式创建的私有模块（类型擦除的堆对象，线程生命周期内复用），核心算法一行不改。AES 块内串行无妨——并行单位是 8MB 块，块间 IV 相互独立。

模块按 `(mode, password)` 经 `StrategyFactory::createModules` 创建（先例 `CompressionWorker.cpp:204`）。因此 **`compressionLoop` 签名从「传模块引用」改为「传 `(mode, password)`」**，模块组装下沉进流水线。这是 GUI 侧唯一改动（`:247` 改传参）。

## 4. 三个角色的改造点

### 4.1 读线程

雏形就是现行装载段（`CompressionLoop.cpp:40-66`）：把"装载 → 读块"留在线程内，"压缩 → 写盘"移交下游。循环体：借块 → DataLoader 填数据 → 分配全局递增的块序号 → 提交任务；借不到块就阻塞（背压来源）。

注意四点：

- `DataLoader::getBlock` 返回内部缓冲引用，下次读取会覆写——提交前必须把数据复制或移动进池块；
- 文件完成时把 `FileTask.processedSizeOffset` 记入**读侧对账单**（有序列表，按文件完成顺序）；
- **空文件不产生任何数据消息**，写线程看不见它：读线程为它发一条"零块结算消息"（只含文件标识，无数据），保证两张对账单按文件 1:1 对齐；
- 读线程结束前把读侧对账单和 `takeBlockSpans()` 的结果交付总指挥——loader 随线程销毁，必须先移交。

### 4.2 写线程（复用 DataExporter，一行不改）

定序器状态只有两样，只被写线程访问，无需加锁：`nextExpectedSequence`（下一个应写序号）、`readyBlocks`（暂存早到结果的表）。取到结果 → 入暂存表 → 从 `nextExpectedSequence` 起凑齐就连环写盘并推进序号。收尾条件：结果队列已关闭**且**暂存表为空；退出前结算最后一个文件。

文件结算：消息带文件标识，写线程见标识变化或收到零块结算消息，把上一文件（或该零块文件）的 `currentFileProcessedSize()` 记入**写侧对账单**，然后 `startNextFile()`。零块结算消息不写任何字节。

异常以 `std::exception_ptr` 随消息存储，写线程统一重抛一次。

DataExporter 连同 fstream 归写线程独占，DataLoader 和目录迭代器归读线程独占——现行类都不用改，只是搬进专职线程。

### 4.3 收尾（复用 CatalogFinalizer，一行不改）

流水线排空后，总指挥做两件事：

1. zip 两张对账单（读侧偏移 × 写侧大小，按文件顺序 1:1 对应）得到 `SizeFillEntry` 表；
2. `finalize(大小表, 读线程移交的目录块位置表, encryption, mode)`。

与串行版 `CompressionLoop.cpp:125-127` 完全同形。"回填先于加密"已焊死在收尾器类内；"加密晚于目录解析"由"收尾在流水线排空后"天然满足。未收尾的归档本就解不开，中断语义不变。

解压路径本计划不动：每输出文件独立 DataExporter 纯追加（`DecompressionLoop.cpp:129、:229`），无回填、无目录区改动。

## 5. 关闭与出错

正常关闭六步，顺序反了会丢尾块或让某端永久等待：

1. 读线程读完全部输入，自然停止提交；
2. join 读线程（收对账单和目录块位置表）；
3. 关任务队列 → 工人排空退出，join 全部工人；
4. 关结果队列 → 写线程刷完尾块退出，join（写侧对账单留在线程对象里，join 后取走）；
5. 总指挥跑 CatalogFinalizer；
6. 关 BufferPool。

排空契约：关闭不打断执行中的任务、不丢弃已入队任务。

出错或用户取消：进度回调（含停止检查）只挂在读线程。读线程异常先行退出 → 总指挥**中止型**关闭 BufferPool（所有等待借出者醒来抛异常）→ 各级按关闭协议收口 → 首个异常在总指挥统一重抛。

## 6. 验收

组件单测（加进 `BuildTest/tests/`，先例 test_bufferpool）：

- 队列：关闭后放入失败；「空且关闭」返回无任务；多进多出不丢不重；
- 池：万级任务计数守恒；异常经结果对象重抛；提交后立即析构不挂死且已提交任务全完成（旧版挂死回归）；`waitIdle` 只等已提交任务；
- 定序：乱序到达按序写出、无缺号、尾块收齐。

集成验收：

- **流水线零字节**：pack/huffman 流水线产物与串行产物逐字节一致（`tool_archivebaseline`，同拆分验收协议），roundtrip 通过；
- GUI 四种模式压解，结果与源一致；
- WSL 下用 ThreadSanitizer 查数据竞争。

## 7. 实施顺序

每步独立可编译、独立按 §6 的字节对比验收：

1. **组件落码**：ThreadPool/ 写队列、池、WorkerEnv，配单测；
2. **最小接入（可选过渡）**：读写暂留串行，仅把块处理段（`:80-85` 两次 encrypt）改成 submit + future 收割——最小改动面先验证池和 WorkerEnv 的正确性与真实收益；
3. **完整流水线**：读写专职线程、消息协议、两张对账单，关闭按 §5；
4. **GUI 参数化**：`compressionLoop` 改传 `(mode, password)`，CompressionWorker 调用点同步。

## 8. 并发正确性备忘

- 谓词读的共享状态必须与修改方共用同一把锁，持锁时求值；
- `wait` 返回即持锁：复查与取出在同一临界区连续完成，不依赖谓词在解锁后仍成立；
- 醒后持锁复查挡伪唤醒与唤醒陈旧；「释放锁 + 登记 + 睡眠」原子（条件变量保证）挡丢失唤醒；
- 任务一律锁外执行，锁内只做队列与计数的极短操作；
- 关闭或退出信号必须进谓词，并配唤醒全部；
- closed 与运行计数是两个问题（还会不会来任务 vs 干完没有），不合并；
- 所有可能抛异常的任务都要有可观测的异常出口，不得在工人栈上裸抛。

## 9. 性能预期（结论版）

- 8MB 大块、计算主导：约 N 倍，调度开销（微秒级）被毫秒级计算淹没；
- 大量小文件：读/写端点本身不随 N 缩放，饱和端约 4~4.5 倍封顶；空转端（队列常空、逐任务唤醒，睡醒往返约 10–20µs）在计算接近纯元数据级时可能跌破 1×；
- 落在哪一端取决于队列有无积压。预留手段（暂不考虑）：读侧突发入队加合并唤醒、工人按字节预算批量取任务、短自旋分级等待；
- 写端大量小文件逐次开关盘落盘，是池救不了的串行项。
