## 1. v1 线程池问题清单（为什么必须重做）

旧文件：`ThreadPool/ThreadPool.h`（79 行）、`_Thread.h`（42 行）、`MonitorTaskQueue.hpp`（61 行）、`src/{ThreadPool,_Thread,MonitorTaskQueue}.cpp` `[4fe0335]`。

1. **析构挂死（最硬）**：`_Thread.cpp:10-16` worker 循环是 `while(true)` + 队列空则永久 `wait`，全代码无停止标志；而 `_Thread.cpp:25` `~Thread()` 会 `join()`。只要触发 `delThread()` 或池析构，worker 卡在 wait、join 永不返回，进程挂死。之前"能用"纯粹因为析构路径从未被走到。
2. **模型反模式——专有队列**：`addTask(trdName, task)` 把任务路由到指定线程的私有队列。3 个块都发给 "worker-1" 时其他线程闲着帮不上忙（负载不均）；调用方还得自己决定发谁、自己 newThread/delThread——调度责任泄漏给用户。
3. **异常即崩进程**：任务里抛异常（AES 模块就 throw `runtime_error`）在 worker 栈上无人 catch → `std::terminate`。
4. **无完成同步**：没有 waitAll/future，"所有块做完才能写文件头/进下一文件"无法表达。
5. **小项**：`threadNums` 与 `threads.size()` 冗余；`MonitorTaskQueue` 只删了移动赋值没删移动构造（rule of five 不完整）。管程本身写法是对的：wait 带谓词防虚假唤醒、锁内 push 后 notify——**队列不是病根，池的模型和生命周期才是**。

## 2. ThreadPool v2 设计（与 Schedule 合并方案）

### 2.1 合并的含义

原 `Schedule/` 的调度职责（Worker 接口 + Strategy + DataConnector）被**共享队列模型**整体取代：不再有"把 Worker 路由给线程"这回事，任务是自包含的 lambda，谁闲谁取。`DataConnector`（块的生产者/消费者握手）职责由 `Y_LightLockQueue` + `BufferPool` 分担。

### 2.2 目标 API（骨架）

```cpp
// 任务签名固定携带 worker 私有环境；普通任务忽略参数即可
using Task = std::function<void(WorkerEnv&)>;

class ThreadPool {
public:
    explicit ThreadPool(size_t n = std::thread::hardware_concurrency() - 2);
    ~ThreadPool();                    // drain 语义：跑完剩余任务再退（压缩工具不能丢任务）

    template <class F>                // F 应可调用为 R(WorkerEnv&)
    auto submit(F&& f)                // packaged_task 包装，返回 future
        -> std::future<std::invoke_result_t<F, WorkerEnv&>>;

    void resize(size_t n);            // 扩：直接加线程；缩：置 exiting + notify，worker 自行退出
    void waitIdle();                  // 队列空 && busy==0（压缩合并/写头前的同步点）

private:
    void workerLoop(std::atomic<bool>& exiting);
    std::vector<std::unique_ptr<std::atomic<bool>>> exitingFlags; // 缩容时逐个置位
    std::vector<std::thread> workers;
    Y_LightLockQueue<std::function<void(WorkerEnv&)>> tasks;      // 共享队列：谁闲谁取
    std::mutex mtx;                   // busy 计数与 idle 判定
    std::condition_variable idleCv;
    size_t busy = 0;
    bool stop = false;
};
```

worker 循环三个关键点（这是 v1 全部三个致命伤的解药）：

```cpp
void ThreadPool::workerLoop(std::atomic<bool>& exiting) {
    for (;;) {
        std::function<void(WorkerEnv&)> task;
        // 1) 从 Y_LightLockQueue 取；队列 closed 且空、或本线程 exiting → return
        task = ...;
        { std::lock_guard lk(mtx); ++busy; }
        task(*env);                   // 2) 锁外执行；异常已被 packaged_task 吞进 future
        { std::lock_guard lk(mtx);
          --busy;
          if (队列为空 && busy == 0) idleCv.notify_all(); }   // 3) waitIdle 的唤醒条件
    }
}
```

submit 的实现要点：`shared_ptr<packaged_task<R(WorkerEnv&)>>` 包住用户可调用物，存入队列的 lambda 是 `[pt](WorkerEnv& env){ (*pt)(env); }`——future 拿结果、异常重抛一次解决。

### 2.3 任务队列：直接采用已定稿的 Y_LightLockQueue

《开发流程与设计细节.md》681-726 行的最终版代码就是对的：wait 带谓词、closed 拒绝 push、Close 之后 drain（取完剩余才返回 false）、锁外 notify。照抄即可；654-668 行那份 `bool readable` 初稿标了"仅逻辑成立"，当废稿处理。实现与调试用 `BuildTest/tests/` 的独立 cmake（对应文档 646 行的意图）。

### 2.4 WorkerEnv —— 线程自己持有模块对象（定稿思路）

```cpp
class WorkerEnv {                    // 每个 worker 一个，随线程生灭
public:
    template <class T, class... Args>
    T& module(Args&&... args) {      // 惰性创建，线程生命周期内复用
        auto key = std::type_index(typeid(T));
        auto it = slots.find(key);
        if (it == slots.end())
            it = slots.emplace(key, std::make_unique<T>(std::forward<Args>(args)...)).first;
        return *static_cast<T*>(it->second.get());
    }
private:
    std::unordered_map<std::type_index, std::unique_ptr<void, void(*)(void*)>> slots;
};
```

要点：
- Aes 构造（一次 SHA256 + 44 字轮密钥扩展）是微秒级、Huffman 构造也是微秒级——**线程生命周期内复用**比每任务新建更省，且完全避开共享；
- 这是"消除共享"方案（每线程一个实例）。被问"如果想多线程共享一个实例呢"时的备用答案是把 `Aes::iv/buffer`、`Huffman::treeRoot` 等下沉为调用参数（"消除可变状态"）。两个答案连着讲最显理解；
- **不要池化 WorkerEnv/工具对象**——构造成本微秒级，池化管理是负收益；该池化的是 8MB 块（见 §5）。

### 2.5 v2 验收测试（写完池先过这四关再接线）

1. 计数守恒：submit 一万个原子自增任务，waitIdle 后断言 == 10000；
2. 异常传播：submit 一个 throw 的任务，断言 `future.get()` 重抛；
3. **析构语义（v1 死穴回归）**：提交任务后立刻析构池，断言不卡死且任务全部跑完；
4. env 复用：用一个计数构造的模块类型，断言同 worker 跨任务只构造一次；`resize` 缩容再扩容不丢任务。

WSL 里 TSan 跑一遍更稳（注意 IV 平台依赖，见 §7.3）。

## 3. BufferPool：现成设施与接线用法

### 3.1 接口语义（`BufferPool/BufferPool.h`）

- `acquire()`：池空则 `cv.wait`——**这就是背压点**；close 后抛 `runtime_error`；
- `release(block)`：`block.clear()` 只清长度保留 8MB 容量（归还路径无 memset），notify 一个等待者；close 后静默放弃；
- `close()`：唤醒全部等待者，用于流水线收尾/出错退出；
- 全局单池：借出方（读线程）与归还方（写线程）不是同一线程，所以**不做 per-thread 池**；一把 mutex 锁 8MB 块的借还，锁开销占比约亿分之一。

### 3.2 接线时的用法

- 池容量 = 在途块上限。建议 `2 × (worker数 + 2)`，内存峰值 ≈ 容量 × 8MB，一目了然；
- 读线程借块填充 → 计算任务产出新块（输出侧同样从池借）→ 写线程写完归还。任何一方借不到就在 acquire 上睡，整条流水线被最慢的一环自然拖住；
- metadata（16KB 级）不值得进池，普通局部 vector 即可。

## 4. Huffman 改造确认

1. **对线程池零依赖**：Huffman 当前不使用任何线程池，接入 v2 无历史包袱；
2. **核心算法零修改**：主流程链路是 `HuffmanCompression.h:21-35` → `Heffman.cpp` 的 statisticFreq/mergeTtabs/genHefftree/saveCodeInTab/treeToPlatUchar/encode。压缩格式是**每 8MB 块独立 Huffman 树**（metadata 随块走），这决定了并行单元就是块——天然适合"每线程一个 Huffman 实例，来一块算一块"；
3. 遗留提醒：`Heffman.cpp:7-11` 构造函数忽略 `threadNums` 参数（历史设计残留），v2 接线时每线程独立实例即可，不必恢复该参数的语义。

## 5. 全局对象池：方案与必要性论证

**池什么、不池什么——判据只有一条：构造成本高的才值得池。**

| 对象 | 构造成本 | 结论 |
|---|---|---|
| Aes / Huffman / WorkerEnv | 微秒级 | 不池。池化管理（借还协议、防双归还）比新建还贵 |
| 8MB 块缓冲（DataBlock） | 分配 ~1-2ms，且反复分配释放造成堆碎片 | **池**（BufferPool） |

**必要性的诚实排序**（被问到就这么答）：
1. **背压与内存峰值控制（主因）**：池容量 = 在途块上限，读线程借不到就睡，防止读盘生产者跑赢计算把内存堆爆；
2. 复用省分配（次因）：8MB 分配 1-2ms vs 单块计算百毫秒级，收益约 1%——是锦上添花不是立项理由。

## 6. 并发不安全模块调研（逐个给结论）

> 调研口径：以"多线程并发调用同一实例/同一模块"为威胁模型。结论先行——
> **全部不安全点都属于"可变成员状态"类，不存在需要重写算法才能并发安全的模块。统一解法是 per-thread 实例（WorkerEnv），核心算法一行不用改。**

| 模块 | 不安全点（行号） | 性质 | 处置 |
|---|---|---|---|
| `Aes` | `My_Aes.h:120 iv[16]`、`:122 buffer`：`mainCircle.cpp:27/42/53/56` 每次 doAes 覆写 | 可变成员状态 | per-thread 实例（WorkerEnv）后天然安全 |
| `Aes`（共享部分） | `My_Aes.h:119 w[44]` 构造后只读；Rcon/colM/S/S2/GF 表全 const | 只读 | 共享读安全，无需处理 |
| `Huffman` | `Heffman.h:65-69` byteCount/threadTabs/hashTab/treeRoot：`HuffmanCompression.h:21-35` compress/decompress 全程读写同一对象状态 | 可变成员状态 | per-thread 实例；每块独立树的格式保证正确性 |
| `HuffmanCompression` | 持有 `unique_ptr<Huffman>`（`:40`） | 随 Huffman | 同上 |
| `DataLoader` | 文件句柄 + 读偏移（`CompressionLoop.cpp:59-64` 串行消费） | **单线程持有**，非算法不安全 | 流水线里归专职读线程 |
| `DataExporter` | 文件句柄 + 写偏移（`CompressionLoop.cpp:72/76`） | 同上 | 归专职写线程 |
| `BufferPool` | mutex + cv 全接口线程安全（`BuildTest/tests` 含 4 线程压力单测） | — | 已安全，直接用 |
| GUI 侧 | 压缩已跑在独立 QThread（`MainWindow_Compression.cpp:473-482`），进度经回调 `emit` 信号，auto connection 跨线程安全 | — | 接线时确认 `m_stopRequested` 为 atomic（取消标志会被写线程读） |
| `StrategyFactory` | 每次 run 构造新模块实例，run 内单线程使用 | — | 现状即安全；v2 下模块创建权移交 WorkerEnv |

**两个补充说明**：
- CFB 模式的块内串行（Cᵢ 依赖 Cᵢ₋₁）不影响上述结论——并行粒度是 8MB 块，不是 16 字节块；chunk 间 IV 互相独立（随机生成、前置于密文），无链式派生，多线程零协调。
- 答辩素材：为什么 CTR 加解密都可完全并行而 CFB 只有解密方向可并行（加密方向每块依赖前一块**密文**，解密方向依赖的密文是现成的）。

## 7. 落地清单（建议顺序）

### 7.1 接线形态（模型二流水线，文档定稿）

```
专职读线程 ──Y_LightLockQueue──> 共享计算池(N worker) ──Y_LightLockQueue──> 专职写线程
      │                                                                      │
      └────────────────── 全局 BufferPool（容量=在途上限=背压）──────────────┘
```

- **判断标准一句话：有状态的阶段用专职线程（状态就是线程的局部变量），无状态的阶段进共享池。** 读线程持有文件流/偏移/EOF；写线程持有 nextSeq/就绪缓冲/文件句柄；worker 来一块算一块什么都不记得。
- **读千万不要做成池任务**：读任务要背压（借不到块得睡），又跑在计算池里 → worker 全睡在池的 acquire 上等 buffer、buffer 等计算完成、计算任务排在队里没人跑——池内互相等待，经典 thread pool starvation。
- **保序写出**：写线程用 `nextSeq + std::map<uint32_t, DataBlock> ready`——块 i 只要自己就绪且之前都写过就能写，不需要"等 i+1 入队"（那个方案会逼出最后一块特判，`isLastOne` 字段整个不需要）。结束条件 = 上游 Close() 且 ready 空。
- **错误传播**：任务 catch 后把 `std::current_exception()` 存进块的 `err` 字段（`std::exception_ptr`），沿数据路径流到写线程统一重抛——AES/Huffman 都会 throw，这条不过去就是 terminate。
- 分两步：先单文件流水线（保序问题锁死在单文件内），文件级并行（13000 个天然并行单元）留二期。

### 7.2 顺序与验收

1. `ThreadPool/` 写 v2 + WorkerEnv（§2.5 四关测试，加进 `BuildTest/tests/`）；
2. 主循环接线（压缩侧先行，解压对称）；GUI 全流程 round-trip（四种策略组合 压缩→解压 与源一致）；
