## 1. 设计目标与决策依据

目标四条：

1. 主循环改为三段流水线：专职读线程 → 计算池 → 专职写线程。
2. 线程池第二版：共享任务队列 + N 个常驻工人 + 每线程私有模块对象（`WorkerEnv`）。
3. 缓冲池接入主流程，作为唯一背压点与内存上限。
4. 写路径拆分：目录区回填/加密收拢到收尾器 `CatalogFinalizer`（4.7），写线程退化为纯追加。

旧实现暴露的问题（决策动机，仅列结论）：

| 问题 | 表现 | 对本设计的约束 |
|---|---|---|
| 结束不可达 | 工人无停止条件永久等待，析构即挂死 | 有一致、可达的关闭协议：关闭标记入谓词 + 唤醒全部 |
| 负载不均 | 任务按线程路由到指定线程 | 统一共享队列，工人主动取任务 |
| 异常终止 | 任务抛异常无人捕获 | 异常封装进任务结果，由提交方或写线程统一重抛 |
| 无完成同步 | 无法表达「全部块完成才能写头」 | 提交返回可等待结果；支持等待全池空闲 |

贯穿原则一句话：有界的「慢」通过背压自动拖住上一级的「快」；内存上界只由缓冲池容量决定（讨论结论见第 3 节）。

## 2. 总体架构（定稿）

```
专职读线程 ──任务队列──> 计算池（N 个工人）──结果队列──> 专职写线程
      │                                                          │
      └────────────── 全局缓冲池（在途块上限）──────────────────────┘
```

| 角色 | 持有的状态 | 职责 |
|---|---|---|
| 专职读线程（上游生产端） | 文件流、读取偏移、文件结束标记、目录迭代器、全局块序号 | 从缓冲池借块、填数据、分配块序号、提交计算任务 |
| 计算池工人（无跨任务状态） | 无（模块对象按线程私有见 4.3） | 从共享任务队列主动取任务，压缩与加密在锁外执行 |
| 专职写线程（下游消费端） | 下一个应写序号、按序就绪的块、输出导出器 | 从结果队列取块，按原始顺序纯追加写回；统一重抛（目录区职责见 4.7） |

三条结构原则（确认稿，对应思路总结第四节）：

1. **有状态的阶段用专职线程，无状态的进共享池。** 文件流、输出序号、回写位置不可共享，归读写专职线程；计算工人每任务独立。
2. **读、写都不做池任务。** 读线程需要借块背压、写线程需要串行有序写盘；放进池会造成池内任务相互等待（池内饥饿）。
3. **背压点只有一个，落在缓冲池。** 两级队列内流动的是不持有大块数据的任务闭包，故队列不设容量上限；内存上限由池容量唯一决定。

## 3. 数据流与内存上界（背压在池的前提）

8MB 数据块只经缓冲池以移动语义流通：借出后由读线程持有 → 随任务闭包交给工人 → 工人处理完归还输入块、产出块随结果流动 → 写线程写完后归还。**在途块总数 = 池容量**，内存峰值 = 容量 × 块大小，与队列长度无关。

该结论成立依赖三条前提，必须同时满足：

1. 读线程先借块、再入队；借不到就阻塞在池上。
2. 每块有且只有一个归还点，且必归还。
3. 任何任务闭包都不自带大块数据。

容量取 `2 × (工人数 + 2)`：最坏情形下每个工人同时持有输入块并可能正在借输出块，即一人占两块；该公式为这一上界留余量。写线程是输出块唯一归还方，只要它不反过来等待被阻塞的工人腾位，就不存在结构性死锁。

## 4. 组件实现决策

### 4.1 任务队列：定稿 `Y_LightLockQueue`（管程形态）

沿用《开发流程与设计细节》§5.2.3 定稿，同一类型建**两个实例**：任务队列（读线程放入、工人取出）、结果队列（工人放入、写线程取出）。结果队列是「多生产者单消费者」：取出侧只有写线程、无竞争，但放入侧仍是多工人并发，**仍需互斥**——不为取出侧另造无锁类型，两个实例共用定稿即可。

语义要点与实现注意事项：

- **管程封装**：队列容器 + 互斥锁 + 条件变量 + `closed` 标记全是私有成员，外部只经取出/放入/关闭三个公开操作访问。任务代码在调用返回后、锁外执行。
- **等待谓词与退出判据是两个布尔式，不可合并**：等待用「队列非空 **或** 已关闭」（析取），决定要不要继续睡；`wait` 返回后仍持锁，再判空——返回「无任务」即意味着「队列空 **且** 已关闭」（合取），调用方此时退出。只看「已关闭」就退出会丢任务，只在「队列空」退出会永远等。
- **关闭方法**：持锁置 `closed` 为真 → 唤醒全部。设置必须在锁内（谓词在锁内读它）。**必须用唤醒全部而非唤醒一个**：若只唤醒一个，被唤醒者复查「空 且 已关闭」后退出，其余睡眠者不会因状态变化而自行醒来，将永久挂睡。
- **放入方法在 `closed` 后拒绝（返回失败）**：这把「关闭之后不再入队」钉死在 API 层，与调用顺序（第 5 节）构成双重保证。
- 队列不设容量上限，生产侧从不因满阻塞 → 只需要一个条件变量，不需要第二把「未满」条件变量。

### 4.2 线程池 v2

接口（与 §5.2.4 定稿一致）：`submit` 提交可调用对象并返回可等待其结果的对象；`resize` 扩容/缩容；`waitIdle` 等待队列空且没有任务在跑；析构先排空再回收线程。

实现要点：

- 工人常驻，死循环从任务队列主动取任务；任务在锁外执行，锁内只做队列检查、取闭包与计数维护。
- **异常不终止进程**：提交用对 `packaged_task` 的共享指针包装，队列内闭包为「调用该打包任务」；异常存入返回的结果对象，由提交方或统一重抛点处理。
- **`waitIdle` 与队列 `closed` 是两回事，不合并**：`closed` 只回答「还会不会来任务」；「全池空闲」用独立的运行任务计数——计数归零且队列为空时，通知空闲等待者。
- **缩容**：给将被回收的工人单独置退出标记并**唤醒全部**——若只唤醒一个，其余睡着的工人可能永不醒来。缩容退出同样进谓词复查（退出标记或 `closed`）。
- **析构 drain**：先允许已提交任务全部完成再回收工人，行为与主动关闭路径一致，需单独测试。

### 4.3 WorkerEnv（每线程私有模块对象）

按类型首次使用创建实例，线程生命周期内复用，存储为类型擦除的堆对象。依据：AES 的密钥扩展表与轮密钥、哈夫曼的频率表与树根是「构造后只读或整树读写」的可变成员状态；每工人一份即可消除全部不安全点，核心算法不改写（AES 的块内串行不影响正确性——并行单位是 8MB 块，块间初始化向量相互独立）。

### 4.4 缓冲池（已实现，接入语义）

- 借出：池空则阻塞等待（**这就是唯一背压点**）；池关闭后抛运行期异常。
- 归还：只清长度、保留容量，并唤醒一个等待的借出者。
- 关闭：唤醒所有等待者，用于流水线收尾或出错退出。
- **与队列关闭语义对照**：任务队列/结果队列是**排空型**关闭（排空后停，不打断已入队任务）；缓冲池是**中止型**关闭（关闭后新借出立即拒绝）。两种关闭都是合法契约，各自实现，不要混用。

### 4.5 写线程与定序器（核心难点）

并行处理必然乱序完成，写线程不能「来一块写一块」。定序器只维护归写线程自己使用的两样状态，**只被写线程访问，无需加锁**：

- `nextExpectedSequence`：下一个应写的块序号；
- `readyBlocks`：按序号暂存早到结果的容器。

工作逻辑：从结果队列取出「序号 + 块」→ 放入暂存表 → 从 `nextExpectedSequence` 开始循环检查，凑齐就连环写盘并推进序号 → 没凑齐就继续等 → 结果队列排空且暂存表为空后收尾。

要点：

- 收尾条件 = 结果队列已关闭 **且** 暂存表为空。
- 文件系统回写按区域拆分：写线程只做数据区纯追加（每块长度直接写真实值）；目录区回填与加密移交收尾器（见 4.7）。
- 异常以 `std::exception_ptr` 随块存储，写线程统一重抛一次，保证错误可观测且不重复处理。
- 结果队列取出侧单消费者无竞争，但不为它造新类型（见 4.1）。

### 4.6 读线程

- 从缓冲池借块、填充数据、分配全局递增的块序号、提交计算任务；借不到块时阻塞（背压来源）。
- 注意输入装载器的内部缓冲会被每次读取覆写、且其取块接口返回内部引用：读线程提交任务前必须把数据复制或移动到池块，否则后续读取会覆盖尚未处理的任务数据。
- 出队每个文件时把该文件的预留槽偏移（`processedSizeOffset`）抄进有序列表——文件队列先入先出、弹出即失，收尾器回填靠这张表（见 4.7）。
- 放入任务若返回「队列已关闭」，读线程据此停止提交（配合第 5 节顺序）。

### 4.7 写路径拆分：收尾器 CatalogFinalizer（目录区唯一改动者）

依据：目录区的回填槽直到**解压**时才被读取，所有目录区改动在逻辑上本就是一个收尾阶段，与块写入无交织必要。现状的别扭在于目录区被三只手先后摸（建档 `HeaderWriter` → `DataExporter` 逐文件回填 → `BinaryStandardLoader::encryptHeaderBlock` 收尾加密，三个类、多个文件句柄），且回填偏移产自读侧目录解析（`EntryParser.cpp:72` 压入文件队列）却要在写侧消费——按原方案得随「文件完成消息」流过整条流水线，消息协议为此复杂化。

回填审计（判据：写的时候知不知道真实值）：

| 回填项 | 现状位置 | 写前已知？ | 处置 |
|---|---|---|---|
| 文件头两个偏移字段 | `HeaderWriter.cpp` | 否 | 保留现状（建档期回填） |
| 每块长度 | `DataExporter.cpp:22-35` 先写 0 再 seek 回填 | **是**（`data.size()` 就在首行） | 假回填：直接写真实值，`thisBlockIsDone` 整个删除，每块省两次 seek，输出逐字节不变 |
| 每文件处理后大小 | `thisFileIsDone`（`DataExporter.cpp:14-20`，调用点 `CompressionLoop.cpp:94-95`） | 否 | 真回填，**推迟到收尾**集中执行 |
| 目录区原地加密 | `encryptHeaderBlock`（`BinaryStandardLoader.cpp:175-216`，调用点 `CompressionLoop.cpp:119`） | — | 收尾最后一步，随 `blockPosition` 一起迁入收尾器 |

拆分后职责：

- **写线程 = 纯数据区追加**：块 = 分隔标志 + 真实长度 + 数据一次写成，完全不知道目录区存在。块携带文件标识，写线程见标识变化即把上一文件累计大小记入「文件 → 处理后大小」表，收工交付。
- **读线程 = 抄偏移表**（4.6 已补条目），收工交付「文件 → 预留槽偏移」。
- **`CatalogFinalizer` = 收尾期目录区唯一改动者**：总指挥串行驱动，先 zip 两张表逐文件回填大小槽，再执行原目录加密逻辑（`encryptHeaderBlock` 与 `blockPosition` 从 `BinaryStandardLoader` 迁入，装载器回归纯读类）。此后目录区所有权清晰：建档 `HeaderWriter` 写、收尾 `CatalogFinalizer` 改，数据阶段无人触碰。
- **任务/结果消息随之简化**：块结构只需 `{文件标识, 块序号, 数据}`，不再需要「文件完成 + 偏移」随块捎带；读写两侧各自积累对账单，收尾时 zip，流水线内部零额外通信。

次序约束（不可乱）：大小槽回填必须在目录加密之前（先加密再回填 = 明文写进密文区）；目录加密必须在目录解析完成之后（解析读明文、`blockPosition` 需收集完）；两者都排在写线程结束之后一次完成，天然满足前两条。中断语义不变：未收尾的归档本就解不开（目录未加密、大小槽为 0）。

解压侧无需此拆分：每输出文件独立 `DataExporter` 纯追加（`DecompressionLoop.cpp:129/:229`），无回填、无目录区。

落地提示：「每块长度直写」与线程池无关，可先行独立落地；非加密模式产物应与改造前逐字节一致，用 `BuildTest/tests/tool_archivebaseline`（roundtrip/verify）验收。

## 5. 关闭与生命周期顺序（必须钉死）

两级队列加一个池，关闭顺序固定如下，顺序反了会丢尾块或让某端永久等待：

1. 读线程读完整个输入，自然结束其提交；
2. 等待读线程结束；
3. 关闭任务队列 → 工人在谓词复查时排空退出，等待全部工人结束；
4. 关闭结果队列 → 写线程刷完暂存表尾块后退出，等待写线程结束；
5. 运行收尾器 `CatalogFinalizer`（回填大小槽 + 目录区加密，见 4.7）；
6. 最后关闭缓冲池。

配合的唤醒矩阵：

| 事件 | 唤醒方式 | 原因 |
|---|---|---|
| 放入一个任务 / 归还一个块 | 唤醒一个 | 只需一个等待者醒来取走 |
| 关闭任务/结果队列 | 唤醒全部 | 每个睡眠者都要复查退出，只唤醒一个会漏 |
| 缩容工人 | 唤醒全部 | 同上，被缩的睡眠工人必须各自复查退出标记 |
| 缓冲池归还 | 唤醒一个 | 只需一个借出者醒来取块 |
| 缓冲池关闭 | 唤醒全部 | 中止型关闭，所有等待借出者都要醒来抛异常 |

「关闭时仍有工人正在执行」是正常状态（排空契约：不打断执行中的任务、不丢弃已入队任务）。健康性由两条保证：① 排空契约；② 排序不变量——关闭后不再入队，由队列 API 拒绝（4.1）与读线程先结束（本节的步骤 1-2）双层保证。

## 6. 并发正确性要点清单

- 谓词读的共享状态必须与修改方共用同一把互斥锁，谓词在持锁时求值；否则是数据竞争。
- 谓词保证的粒度 = 一个临界区：`wait` 返回即持锁，复查与「取出」必须在同一临界区内连续完成，无人能插；不依赖「谓词为真」在解锁后仍成立。
- 三类错误的防御分居两侧：醒来后的持锁复查（循环）挡伪唤醒与唤醒陈旧；入睡时「释放锁 + 登记 + 睡眠」原子（由条件变量等待方法保证）挡丢失唤醒。关闭/缩容用唤醒全部后的多醒属正常复查路径，不是缺陷。
- 等待谓词用析取（非空 或 已关闭），退出判据用合取（空 且 已关闭），两者不可混。
- 任务一律锁外执行；锁内只做队列与计数的极短操作，临界区最小。
- 两张等待列表要分清：条件变量的等待列表（睡眠者）与互斥锁的等待列表（抢锁失败者）；队列空时的等待由条件变量释放锁并挂起，抢锁失败由操作系统在互斥锁上排队，二者都不需要额外唤醒。
- 关闭或退出信号必须进谓词，并配唤醒全部。
- 关闭后不得入队：API 拒绝 + 调用顺序，双层保证。
- `closed` 与运行任务计数是两个布尔、两个问题（还会不会来任务 vs 干完没有），不合并。
- 消除共享可变状态：不安全点全是模块可变成员状态，每工人一份 `WorkerEnv` 即可。
- 所有可能抛异常的任务都必须能将其异常送入可观测路径（提交方结果对象或写线程统一重抛），不得在工人栈上裸抛。

## 7. 验收与落地步骤

单元测试（加入测试工程，先例 `BuildTest/tests/`）：

1. 队列 `Y_LightLockQueue`：关闭后放入返回失败；取出在「空 且 已关闭」返回无任务；多放入多取出不丢不重。
2. 线程池计数守恒：提交万级任务，完成后计数一致，无丢失无重复。
3. 异常经结果对象正常重抛，进程不被终止。
4. 提交后立即析构：不挂死，且已提交任务全部完成（对应旧版「析构挂死」回归）。
5. 空闲等待语义：`waitIdle` 只等当前已提交任务，不等未来提交。
6. 写线程定序：乱序到达按序号写出、无缺号、尾块收齐。

集成验收：

1. 图形界面四种压缩策略后解压，结果与源一致。
2. 写路径拆分零字节变更：非加密模式（pack/huffman）`tool_archivebaseline` 产物与拆分前逐字节一致，roundtrip/verify 通过。
3. Windows 子系统 Linux 下用线程消毒器（ThreadSanitizer）做数据竞争检查。

落地分两阶段：先按组件单测通过（任务队列、线程池、缓冲池各自单独测试），再接主循环；主循环接入先做单文件流水线，文件级并行放二期。

## 8. 技术遗留事项

- 初始化向量生成是唯一 Windows 平台依赖（Windows 加密 API），接入测试前提取为平台无关函数（Windows 分支保留原调用，其他平台读 `/dev/urandom`）。
- 相对头文件包含依赖编译参数中存在仓库根的直接子目录，可改为规范相对包含 + 追加包含路径。
- 构建入口为测试工程（MinGW + 静态 Qt，发布配置）。
- 类名 `Y_LightLockQueue` 不满足语义化命名约定（无含义前缀 + 含义不明的后缀）。当前为既有定稿、未落码，**落码时建议改名**为语义化类名（如 `BlockingTaskQueue`），同步修改本计划与《开发流程与设计细节》§5.2.3，两处一致即可。

## 9. 性能估算与预留优化（本期不实施，仅存底）

> 本节是讨论底稿存档，**不是本期实现要求**。结论先行：先按 §7 落地并测量，再决定是否启用下述优化。基线一律取「完全串行、无线程池」。

### 9.1 参数定义（口径先钉死）

设每个「任务单元」独立计量，串行基线 = 单线程顺序做完 读→压缩/加密→写 三件事：

| 记号 | 含义 | 说明 |
|---|---|---|
| i | 读一个单元花费 | 含打开文件 + 读 + 关闭，单线程读端 |
| c | 计算一个单元花费（压缩 + 加密） | 可被 N 个工人并行 |
| w | 写一个单元花费 | 单线程写端 |
| N | 工人线程数 | 计算并行度上限 |
| s | 每单元调度开销 | 两个极端取不同量级 |

吞吐口径：串行基线吞吐 = `1 / (i + c + w)`；流水线稳态吞吐 = `1 / 每单元最慢级`。

### 9.2 两个调度极端（先分清分别指什么）

- **饱和端**：任务有积压、队列永不空，工人从不睡去。s 只剩互斥锁往返（锁竞争），约 **0.1–1 微秒/单元**。
- **空转端**：任务逐个到来，工人做一件睡一次、逐任务被唤醒。每单元支付一次完整「睡-醒」上下文开销（条件变量唤醒 + 两次系统调用），约 **5–20 微秒/单元**；且由单个工人串行承担——任务太小，工人做完就睡，其它工人来不及参与，**并行度实际坍缩**。

每单元流水线墙钟时间 ≈ max(读端 i, 计算端 (c+s)/N, 写端 w)，吞吐提升比率：

```
R = (i + c + w) / max(i, (c+s)/N, w)
```

### 9.3 场景估算

**场景一：粗粒度（8MB 大块，CPU 受限）**。假设 N=8，c ≈ 80ms（8MB 压缩 + 加密），i ≈ w ≈ 5ms。调度开销（微秒级）相对毫秒级计算完全可忽略，两个极端收敛到同一结果：

| 端 | 墙钟/单元 | 比率 R |
|---|---|---|
| 饱和端 | (80 + ~0)/8 ≈ 10ms | 90/10 ≈ 9× |
| 空转端 | 同上（睡醒成本被 80ms 淹没） | ≈ 9× |

结论：粗粒度下提升约等于 N（接近线性），调度不是瓶颈，两个极端无差别。

**场景二：细粒度（大量极小文件）**，两套假设：

假设 A（每文件计算仍有点分量）：c = 50µs，i = w = 20µs（每端一次开/读/关），N=8。串行 = 90µs。

| 端 | 每单元墙钟 | 比率 R |
|---|---|---|
| 饱和端 | max(20, (50+0.5)/8 ≈ 6, 20) = 20µs | 90/20 ≈ 4.5× |
| 空转端 | 单工人串行 ~（睡醒 15µs + 50µs），墙钟 ≈ 65µs | 90/65 ≈ 1.4× |

假设 B（每文件计算极小）：c = 10µs，i = w = 5µs。串行 = 20µs。

| 端 | 每单元墙钟 | 比率 R |
|---|---|---|
| 饱和端 | max(5, (10+0.3)/8 ≈ 1.3, 5) = 5µs | 20/5 = 4× |
| 空转端 | 单工人 ~（15 + 10）= 25µs | 20/25 ≈ 0.8×（比串行还慢） |

### 9.4 何时跌到 1× 以下（跨界条件）

空转端劣于串行的条件是睡醒开销能盖过「读 + 写 + 计算」本身，数量级上：

```
每任务计算 c ≲ 睡醒往返开销 s（约 10–20µs）
且队列长期空、逐任务唤醒
```

任务越碎、工人越常睡，越逼近这一端。粗粒度块永不触发；极小文件在计算接近纯元数据级时才触发。真实压缩任务对 4KB 文件的 c 大约几十微秒，落在「略好于 1×」与「~1.5×」之间，尚未跌穿，但离跌穿不远。

### 9.5 决定性变量：场景落在哪一端

这不是二选一的彩票。落在哪端取决于**任务到达速率 vs 工人消费速率**：

- 读线程单线程逐文件产任务（i 每秒几十 k 的上限），而 8 个工人合计消费能力远高于此 → 队列常空 → 落在空转端，睡醒抖动把提升啃到接近 1×。
- 只要让队列出现积压（一批文件同时入队），工人保持饱和 → 跳回饱和端。

这正是「合批」的量化意义：把 K 个文件并成一个任务，每任务的 c 放大 K 倍、任务数除以 K，睡醒开销被摊薄 K 倍——同一套吞吐模型下，把场景从空转端（~1×，甚至 <1×）推回饱和端（4× 上下）。注：此处「并成一个任务」指调度级一次取出 K 个任务来执行（见 9.8），不是跨协议块的数据级合批（已在协议层否决）。

两点提醒：以上是数量级估算，i/w/c 需用你的实测替换；写端若是大量独立小文件的逐次开/关/落盘，w 本身也是不随 N 缩放的串行项，池无论如何改都盖不住它。

### 9.6 不含调度的理想上界（对照天花板）

把 9.2 公式中的 s 置零即得调度免费的天花板：

```
R_理想 = (i + c + w) / max(i, c / N, w)
```

实际 R 只会比它低。边界情形由公式直接推得（无需实测）：

| 情形 | 条件 | R_理想 |
|---|---|---|
| 计算主导 | c ≥ N·max(i, w) | 接近 N（并行充分兑现） |
| 三端均衡 | i ≈ w ≈ c | ≈ 3 |
| 端点主导 | c 相对 i、w 可忽略 | 约 1~2 |

推论：流水线只让三段重叠，**能摊到 N 个核上的只有 c**——这解释了 9.3 场景二饱和端为何止步在 4~4.5×（读/写端点锁死了分母）而不是 N。大量极小文件场景 c 占比小、i 与 w 才是大头，即使调度免费，收益天花板也在个位数倍以内；只有计算为主（8MB 大块）才逼近 N 倍。若一端严重倾斜（如 w ≫ i），上界收敛到 1 附近，重叠救不回来。

### 9.7 设计结论：不引入固定专职工人，保留对称池

讨论中提出「只放一个特殊工人一直单线程干活，少受调度影响」。**否决，理由存档：**

- 调度税按「睡→醒」事件计数，不按池里存在的线程数计数；睡着的工人是零调度开销，空闲的 N-1 个工人并不制造税。
- 空转端下，对称池 + 唤醒一个**本来就是单工人行为**：工人执行完回队，队列非空就直接弹下一个（不睡、不付税）；生产者趁它忙时入队并唤醒，唤醒落空只是空操作。真正付的一次往返只在「工人入睡后、下一任务才到」的间隙出现。
- 固定单工人会在饱和端把吞吐钉死在单核。对称池能自适应爬升：单工人忙不过来、任务滞留时，后续入队的唤醒会把睡着的工人逐个拉起，参与数自动随积压增长。
- 若担忧「突发后只有最先醒的一个在批处理、其余爬起来慢」，那是**唤醒粒度**问题，归 9.8 的合并唤醒管，不是专职线程能解决的。

### 9.8 预留优化：调度合批（不碰协议）

数据级合批在文件协议层不可行（协议复杂、改动面大），已否决。调度级合批不触碰协议，只改「入队 / 取任务 / 等待」三处调度行为，若测量显示 s 相对 c 占比高再启用：

1. **读线程突发入队 + 合并唤醒**：入队侧本就单线程，一次持锁放入一批；唤醒按「空 → 非空」转换触发，唤醒数量取 min(本次入队数, 池中工人数) 以内即可——超出实际睡眠者的唤醒是空操作、无害，不必精确知道睡眠人数。若只唤醒一个，突发会先被单核批处理掉，其余工人要等下一次空→非空才被拉起，并行爬升慢。
2. **工人按字节预算批量取出**：一次持锁从队首连续弹出任务，累计已用字节达预算（或个数达上限）即停，锁外逐个执行。按字节而非固定个数，批时长随文件大小自适应，避免一批撞上大文件把单个工人拖太长。这正是 9.5 里「c 放大 K 倍、睡醒摊薄 K 倍」的实现落点。
3. **短自旋分级等待**：队列空时先用短窗口自旋探测「入队信号」原子计数（不加锁、不抢互斥锁），预算耗尽再入条件变量入睡。自旋不能持锁、窗口要短（全员空等时 N 个核都在转）；「定时复查」中间层只在怀疑存在「改了状态却没唤醒」的遗漏路径时才需要，正常设计下入队必唤醒，不加。

激活顺序建议：先测量每任务调度税相对 c 的比例；空转停顿区制是主因则启用 2、3，突发并行爬升慢再启用 1。

## 一句话收束

生产与磁盘的串行状态归专职线程，无状态计算进对称池并行，乱序结果由唯一写线程按序号重组；内存上限由缓冲池唯一决定，两级队列用同一管程式队列承载闭包、只在消费者侧等待；数据区由写线程纯追加、目录区由收尾器在排空后一次改定（回填先于加密）；关闭按「等待谓词析取、退出判据合取、唤醒全部、关闭后不入队」逐级收口，让每一级的慢自动拖住上一级的快。
