# 1. 用户需求与程序概览

## 1.1 用户需求

> 应用需要什么功能？

我们需要尽可能给用户提供自由的压缩选项。

【问题 A1】  
是否需要加密？用什么算法加密？这在 GUI 界面中分别通过一个勾选器和列表选择器让用户操作。

**实际实现**：使用 AES-128；密码经 SHA-256 后取前 16 字节作为密钥。

【问题 A2】  
在压缩时，可能需要处理多个文件一起压缩的情况。将多个文件整合成一个压缩包？所有文件分别独立成一个压缩包？或是在应用内可选择分类生成多个压缩包？需要提供一个选项供用户选择。

**实际实现**：支持将多个文件或目录压缩到单个 `.sy` 文件。

【问题 A3】  
~~对于编码结构，用户可以选择是否将其独立成一个文件存放。~~（已不纳入考虑）

【问题 A4】  
使用 RSA 加密可以实现特定用户间的数据加密传输。这时需要提供一个 RSA 密钥生成器。

**实际实现**：RSA 未实现。

【问题 A5】  
可以选择从右键菜单栏中直接启动压缩任务。

**实际实现**：已提供 Qt GUI；解压遇到同名文件时跳过，不覆盖。

## 1.2 技术名词

技术名词解释：

- **AES 加密**：高级加密标准，对称性加密算法。本程序使用 AES-128，128bit 密钥，10轮处理。
- **RSA 加密**：非对称性加密算法。（备选，未实现）->网络通信专用，pc算力无实现可能
- **流加密**：逐字节加密处理。（备选，未实现）
- **Huffman 编码**：基于前缀码的无损压缩算法。基于自然语言重复性实现压缩。
- **BWT 编码**：基于后缀数组的压缩数据预处理算法。（备选，未实现）
- **LZ77**：使用滑动窗口建立三元组的压缩算法，可作为 Huffman 压缩的前置操作。（备选，未实现）
- **Qt**：C++ 的 GUI 框架，跨平台兼容。SFCv2.0.0已实现
- **文件头**：包含压缩文件基本信息的数据结构。
- **位图(bitmap)**：按位存储状态。
- **信号与槽**：Qt 框架的核心思想，响应式 GUI 编程。
- **锁**：控制临界区的变量，持有锁的线程可以进入临界区。
- **条件变量**：核心为休眠队列，通过信号唤醒队列中的线程。
- **信号量**：类似 Minecraft 的红石比较器，或 AE 的发信器。控制进入临界区线程的数量。
- **死锁**：多个线程争抢锁的形式构成单向环图的状况。造成线程永久的休眠。
- **系统调用**：由操作系统提供给应用程序的接口。通常是受限操作，由操作系统执行。

# 2. 程序初步设计

## 2.1 程序结构及要点

**Compress/Decompress_System**（已实现）

- 负责压缩与解压。
- 核心类：`CompressionLoop`、`DecompressionLoop`
- 调用 Huffman 模块和 AES 模块

**Encryption/Decryption_System**（已实现）

- 负责加密与解密工作。
- 核心类：`Aes`
- 支持 SHA-256 密钥派生

**BufferPool**（部分实现）

- 缓存以上两者的输出（通信缓存池、打包缓存池、解包缓存池）
- 充当可接受线程管理器动态调度的对象
- 每个线程组独立使用一个缓存池
- 加入大小限制和溢出处理机制
- 充当接收输入并缓存/主动抛出的作用

**实际实现**：数据通过 `Y_flib::DataBlock`（`std::vector<uint8_t>`）同步传递。

**ErrorCollector**（未实现）

- 负责对错误的检测与收集，生成并且输出相关错误报告(日志)
- 当前使用 `std::runtime_error` 抛出异常，由主程序捕获

## 2.2 模块设计

### Encryption 加密模块设计

技术点(适配技术)：

1. **密钥 hash 处理**（已实现）
   
   用户输入任意长度的密码后，程序调用 SHA-256 算法对密码进行哈希处理，生成 32 字节的哈希值，然后取前 16 字节作为 AES-128 的实际密钥。这样做的好处是支持任意长度密码，同时保证密钥长度符合 AES 要求。

2. **CFB 模式**（已实现）
   
   AES-CFB 不需要 PKCS#7 填充，数据长度保持不变。

3. **缓存池**（已实现）
   
   使用 `Y_flib::DataBlock` 作为数据缓冲，这是一个动态数组，可以自动扩展和管理内存。

### Compression 压缩模块设计

1. **频率统计**（已实现）
   
   遍历数据块中的每个字节，统计 0-255 各个字节值出现的次数。程序支持多线程分别统计不同数据块，最后合并统计结果。

2. **树构建**（已实现）
   
   使用最小堆（优先队列）数据结构，每次从堆中取出频率最小的两个节点，合并为一个新节点，新节点的频率为两者之和。重复此过程直到只剩一个节点，即为 Huffman 树的根节点。

3. **编码解码**（已实现）
   
   编码过程：从根节点开始递归遍历 Huffman 树，向左走记录 0，向右走记录 1，到达叶子节点时即得到该字符的编码。
   
   解码过程：从根节点开始，按编码位（0 或 1）在树上行走，到达叶子节点时输出对应字符，然后回到根节点继续处理下一个编码。

### UnitManager 单元管理器

- 示意：Huffman-(1)>Aes-(2)>.sy 文件(实际为二进制)
- 虚拟接口类的设计：

**实际实现**：`CompressionLoop`、`DecompressionLoop` 顺序调用处理模块；`DataLoader`、`DataExporter` 使用 8MB 缓冲区同步读写。

### 文件模块设计

1. **状态检测器**：检测加密状态（Y/N）。监控文件压缩进度。

   **实际实现**：通过 `Header.strategy` 记录处理策略。

2. **文件信息读取器**：将文件的整个文件头读取到程序缓存中，并进行相关检查。监控文件解压进度。

   **实际实现**：由 `BinaryStandardLoader` 读取文件头和目录块。

- 关于数据块类：

**实际定义**：`Y_flib::DataBlock` 是 `std::vector<unsigned char>` 的类型别名。

设计阶段定义（未完全实现）：
```
  vector<uint8_t> data    // 数据（二进制），可以先给定一个基础大小，避免频繁扩容
  uint32_t sequence_tag   // 顺序标签
  bool is_terminated      // 终止信号
  uint8_t header_flags    // 文件头标志位
  string source_tag       // 来源标签（如"COMPRESS", "AES"）
  string error_message    // 错误信息
```

- **偏移量记录方式和相关规则**

  - 维护：在文件头中存储数据文件的文件名初始大小，解压时逐步递减，直至字节数不足。
  - 另外，需要在压缩时动态维护已压缩文件的大小，待数据块抛出进程结束信号时写入文件头中预留好的偏移量的数据上，可以用于多文件下的 huffman 与 aes 的部分功能实现

**实际实现**：偏移量使用 `uint64_t`，写入时维护并回填预留位置。

### GUI 模块设计

目标：GUI 只负责交互与调度，压缩/解压核心逻辑继续复用 `Y_Manager` 与 `CompressorFileSystem`，避免形成一套 CLI、一套 GUI 的重复实现。

**当前实现**：
- `MainWindow` 管理界面和后台 `QThread`；`CompressionWorker` 调用核心流程并回传进度。
- 支持 `HuffmanAES`、`HuffmanOnly`、`AESOnly`、`PackOnly`，解压时按 `Header.strategy` 自动选择。
- 支持压缩/解压分页、拖放、取消和界面本地化。
- 路径统一经 `EncodingUtils` 在 UTF-8 与 `std::filesystem::path` 间转换。
- 使用 Qt 6.2.4 及其匹配的 MinGW；开发使用动态部署，发布使用静态单 exe。


# 3. 文件格式与底层细节

## 3.1 技术整合与文件格式

主要技术：

- **加密：**
  - aes-128：128bit 密钥，十轮处理。

- **压缩：**
  - huffman：基于自然语言重复性的压缩算法

- **控制：**
  - thread/buffer:
    - 线程与线程、模块与缓存池之间的组合与调度

- **文件格式设计：**

```
┌─────────────────────────────────────────────────────────┐
│                      .sy 文件结构                        │
├─────────────────────────────────────────────────────────┤
│ [文件头 19字节]                                          │
│ ├─ magicNum_1 (4B)  : 0xDEADBEEF 文件标识               │
│ ├─ strategy (1B)    : 压缩策略号                        │
│ ├─ version (1B)     : 版本号                            │
│ ├─ headerOffset (1B): 文件头偏移（保留）                │
│ ├─ directoryOffset(8B): 目录块起始偏移量                │
│ └─ magicNum_2 (4B)  : 0xDEADBEEF 校验标识               │
├─────────────────────────────────────────────────────────┤
│ [目录块区域]                                             │
│ ├─ [分割标准 25B] → blockSize + IV                      │
│ ├─ [目录块数据] → 文件/目录标准（AES-CFB 加密）         │
│ ├─ [分割标准 25B]                                       │
│ ├─ [目录块数据]                                         │
│ └─ ...                                                  │
├─────────────────────────────────────────────────────────┤
│ [数据区]                                                 │
│ ├─ [分割标准 25B] → blockSize + IV                      │
│ ├─ [Huffman 树数据] → AES-CFB 加密，无填充              │
│ ├─ [分割标准 25B]                                       │
│ ├─ [压缩数据] → AES-CFB 加密 + 末尾1字节有效位数        │
│ └─ ...（重复以上结构直到文件结束）                      │
└─────────────────────────────────────────────────────────┘
```

**实际实现**：

每个数据块都具有 Huffman 编码表，且在数据区的末尾添加了一字节标识符，以区分 Huffman 填充与有效数据。

### 文件头结构（Header）

| 字段 | 类型 | 大小 | 说明 |
|------|------|------|------|
| magicNum_1 | uint32_t | 4字节 | 魔数 `0xDEADBEEF`，文件标识 |
| strategy | uint8_t | 1字节 | 压缩策略号（当前为 0） |
| version | uint8_t | 1字节 | 版本号（当前为 2） |
| headerOffset | uint8_t | 1字节 | 文件头偏移（保留） |
| directoryOffset | uint64_t | 8字节 | 目录块起始偏移量 |
| magicNum_2 | uint32_t | 4字节 | 魔数 `0xDEADBEEF`，校验标识 |
| **总计** | | **19字节** | |

### 目录块结构

目录块由多个"标准"（Standard）组成，每个标准以 `FlagType` 标识符开头：

#### 文件标准（FlagType::File = 1）

| 字段 | 类型 | 大小 | 说明 |
|------|------|------|------|
| flag | uint8_t | 1字节 | 标识符 `1` |
| nameSize | uint32_t | 4字节 | 文件名长度 |
| name | char[] | 变长 | UTF-8 编码文件名 |
| originalSize | uint64_t | 8字节 | 原始文件大小 |
| compressedSize | uint64_t | 8字节 | 压缩后大小（压缩时回填） |
| **基础大小** | | **21字节** | 不含文件名 |

#### 目录标准（FlagType::Directory = 0）

| 字段 | 类型 | 大小 | 说明 |
|------|------|------|------|
| flag | uint8_t | 1字节 | 标识符 `0` |
| nameSize | uint32_t | 4字节 | 目录名长度 |
| name | char[] | 变长 | UTF-8 编码目录名 |
| childCount | uint32_t | 4字节 | 子元素数量 |
| **基础大小** | | **9字节** | 不含目录名 |

#### 分割标准（FlagType::Separated = 2）

| 字段 | 类型 | 大小 | 说明 |
|------|------|------|------|
| flag | uint8_t | 1字节 | 标识符 `2` |
| blockSize | uint64_t | 8字节 | 数据块大小 |
| iv | uint8_t[16] | 16字节 | AES 加密初始化向量 |
| **总计** | | **25字节** | |

#### 逻辑根目录标准（FlagType::LogicalRoot = 3）

| 字段 | 类型 | 大小 | 说明 |
|------|------|------|------|
| flag | uint8_t | 1字节 | 标识符 `3` |
| nameSize | uint32_t | 4字节 | 根目录名长度 |
| name | char[] | 变长 | UTF-8 编码根目录名 |
| childCount | uint32_t | 4字节 | 子元素数量 |

#### Windows 链接标准（FlagType = 4/5/6）

| 字段 | 类型 | 大小 | 说明 |
|------|------|------|------|
| flag | uint8_t | 1字节 | `4`=文件符号链接，`5`=目录符号链接，`6`=Junction |
| nameSize | uint32_t | 4字节 | 链接名长度 |
| targetSize | uint32_t | 4字节 | 目标路径长度 |
| name | char[] | 变长 | UTF-8 编码链接名 |
| target | char[] | 变长 | UTF-8 编码、链接自身记录的原始目标路径 |
| **基础大小** | | **9字节** | 不含变长字段 |

压缩扫描遇到 Windows 符号链接或 Junction 时，只读取重解析点自身并写入上述元数据，不进入或解析目标。相对目标保持相对形式，绝对目标保持绝对形式；目标位于归档根目录之外、目标不存在或链接之间形成循环都不会阻止归档。解压时先恢复普通文件和目录，再按记录的目标字符串重建链接。目标在另一台机器上不存在时，恢复结果是正常的悬空链接。

### 数据区结构

每个文件的数据由多个数据块组成，每个数据块结构如下：

```
[分割标准 25字节]
├─ flag: 2
├─ blockSize: Huffman 树数据大小
└─ iv: AES 加密 IV（若未加密则为全零）

[Huffman 树数据]
└─ AES-CFB 模式加密的序列化 Huffman 树（无填充）

[分割标准 25字节]
├─ flag: 2
├─ blockSize: 压缩数据大小
└─ iv: AES 加密 IV（若未加密则为全零）

[压缩数据]
├─ AES-CFB 模式加密的 Huffman 编码数据（无填充）
└─ 末尾一字节：有效数据位数标识
```

**加密说明**：采用 AES-CFB 流模式加密，无需 PKCS#7 填充，数据长度保持不变。

### 目录块加密

当启用加密时，目录块会被加密：

1. 压缩时：目录信息写入完成后，读取整个目录块，AES 加密后覆写回原位置
2. 每个分割标准中的 `iv` 字段存储该块的加密初始化向量
3. 解压时：读取目录块，检查 `iv` 是否非零，若非零则先解密再解析

### 常量定义

| 常量名 | 值 | 说明 |
|--------|-----|------|
| MAGIC_NUM | 0xDEADBEEF | 文件魔数 |
| BUFFER_SIZE | 8MB | 数据块大小 |
| HEADER_BUFFER_SIZE | 16KB | 目录缓冲大小 |
| STRATEGY | 0 | 当前压缩策略号 |
| VERSION | 2 | 当前写入版本号（2：增加 Windows 文件符号链接、目录符号链接和 Junction 标志） |
| MIN_SUPPORTED_VERSION | 1 | 最低可读取版本；v1 普通文件归档仍可读取，旧版链接元数据因语义不完整会被拒绝 |
| DIRECTORY_STANDARD_SIZE_BASIC | 9字节 | 目录标准基础大小 |
| FILE_STANDARD_SIZE_BASIC | 21字节 | 文件标准基础大小 |
| SEPARATED_STANDARD_SIZE | 25字节 | 分割标准完整大小 |
| LINK_STANDARD_SIZE_BASIC | 9字节 | Windows 链接标准基础大小 |

# 4. 当前实现

## 4.1 算法与文件处理

### AES 加密实现

- 密码经 SHA-256 后取前 16 字节作为 AES-128 密钥。
- 密钥扩展生成 44 个轮密钥字，完成 10 轮 AES 运算。
- GF(2^8) 乘法使用预计算表。
- 数据块采用 CFB 模式，不需要 PKCS#7 填充。

### Huffman 压缩实现

- 统计 256 种字节频率，通过最小堆构建 Huffman 树。
- 递归生成编码，并以前序方式序列化、反序列化树。
- 单字符数据块固定使用编码 `0`。

### 文件头实现

1. 记录文件头和数据块的偏移量

2. 记录压缩方案：加密方式/有无加密、压缩方式。

3. 在文件头记录文件的目录结构、偏移量：其中目录结构使用前缀索引（将会在前缀记录所有文件目录，其对应数据区存储包含文件后缀的文件名）、偏移量单独在文件名后存储（为每个节点预留 2\*8 字节，分别存储文件压缩前后大小）

4. 对于动态获取的偏移量的实时存储（接到结束信号后将压缩偏移量从缓冲区写入文件）。

   **实际实现**：
   - 方案：读取文件目录之后直接在文件头中逐个处理对应文件（服务于数据偏移量更新），并且在预留好的位置修改压缩后大小。（不影响数据区写入数据。）
   - 至此，实现无临时文件的方案已经完善。

5. **文件头信息写入**

   - 实现细则：

   - 1. 文件信息存储标准：|文件标|4B 文件名大小偏移量|文件名|----|

     - 文件标为数值 `0`：为目录。需要写入：|4B 第一级文件数量|
     
     - 文件标为数值 `1`：为文件。需要写入：|8B 原文件大小|8B 压缩后偏移位|。其中压缩大小暂时作为占位区。

     - 文件标为数值 `2`：为分割偏移量,是为加密/分块特化的标签
       - 写入:|1B 标识符||8B 偏移量||16B iv 加密头|
       - 如果读到偏移量为零，说明此时已经写入到最后一个不足 8MB 的块（按目录的残余偏移量来读取，包含只有一块的情况）aes 的加密头会写入到预留位置
     
     - 文件标为数值 `3`: 为逻辑根目录标记，与普通目录存储仅有标识符不同
     
     - 文件标识符为数值 `4`、`5`、`6`：分别为 Windows 文件符号链接、目录符号链接和 Junction
       - 存储标准：|文件标|4B 文件名长度|4B 目标路径长度|文件名|原始目标路径|
       - 扫描时不进入、不解析链接目标；解压完成普通条目后直接按记录创建链接

**实际实现**：

`FlagType`（底层 `uint8_t`）定义 `Directory(0)`、`File(1)`、`Separated(2)`、`LogicalRoot(3)`、`SymbolicLinkFile(4)`、`SymbolicLinkDirectory(5)`、`Junction(6)`。本项目只实现 Windows 重解析点语义，不再保留 Linux 符号链接分支。基础大小分别见第3章格式表。

### 压缩前运行流程

- 0. 文件头开始与结束均需要写入魔数 `0xDEADBEEF`。

- 1. 目录：读取后写入对应的存储标准，并且在缓冲区中缓存一个文件数量。

- 2. 文件：读取后写入对应的存储标准

- 3. 搜索方案：采用 BFS。在上述 0、1、2 作为必要操作的条件下，搜索目录。

  I:

  - 如果搜索到文件：直接写入。
  - 如果搜索到目录：进入该目录并且记录其中第二级文件数量以及该目录的完整路径到队列备用。并且按标准写入文件。

  II:记录完数量后：返回，继续搜索第一级目录,重复操作 I,直到第一级搜索完成。

  III:处理队列，接着按照队列已存储的路径打开下一级目录，以先前获取的第二级文件数量及其所在目录的路径，按顺序读写对应的文件数据，直至文件数量 num--耗尽为止。

  IV：重复上述操作直到读取完成。

  以上 I~III 解决了解压文件时如何按照顺序读取文件及其目录的问题。

  V:特别地，可以为目标文件提供一个逻辑根目录（同名或命名），以便始终遵循如上顺序读写数据（或者单独存储根目录下的子文件/目录数量）。

  VI:文件头开始为写入文件头偏移量预留位置，文件头写入完毕后更新这个偏移量

  VII:如果需要加密，则按照偏移量在原内容上进行覆写

**实际实现**：

`EntryProcessor` 使用 BFS 扫描目录，写入文件或目录标准，并按 16KB 分割目录数据。

偏移量通过 `seekg/seekp` 定位；写入位置由 `tempOffset` 同步维护，文件完成后回填大小。

### 文件头信息获取

1. **通用部分**：
   - I: 打开文件直接读取魔数，并且按照文件头方案读取策略等数据，如文件头以及文件目录的偏移量
   - II: 定位到文件目录起始位置，根据分隔符将文件目录信息按块读进内存中处理
   - III: 读取完 文件信息/压缩后数据 之后，记录此处的偏移量以便下一次处理时直接定位（往返定位）

2. **压缩时的信息获取**：
   - 在完成通用部分的基础上：
   - 需要获取并且拼接文件的路径，通过某种传输方式发送给压缩模块处理。
   - 需要在获取到数据块结束标志时写入末尾偏移量（统一以当前文件大小存储，并且在循环中更新下一次起始位置为上一次末尾偏移量）
   - 加密时确保数据块一次性处理完之后再交予写入程序写入文件中，预计更换 aes 为 cfb 模式的实现（已实现）

3. **普通解压时的信息获取**：
   - 在完成通用部分的基础上：
   - I:对于文件：获取其在数据区的偏移量并且定位到数据区对应的位置读取数据
   - II:对于文件夹：获取它携带的子文件数量信息并且记录到"下一层文件数量"，同时创建文件夹以及其 details 信息类对象，并将对象存入到队列中备用
   - III:按照以上方式读取数据直到耗尽当前目录的"文件数量"（根目录以及多文件根目录的边界情况：使用了加入逻辑根节点的方式解决）
   - IV:循环以上操作，并且注意比对此时的读取位置与文件头中记录的文件目录偏移量。

4. **解压时数据获取**：
   - 对于被加密的数据块：按偏移量分割，分块读取数据，解密后存储在内存中（需要专门编写一种新的读取函数，不过逻辑是类似的）
   - 加密后的目录需要被读取到内存后经过解密处理传回文件处理模块使用
   - 内存中保留拼接好的路径，抛弃已处理完的文件目录数据（动态数组采用默认 9KB 大小，实际上最多只能读到 8KB+600B 左右,配合 clear 恢复 size=0，还需要 resize 确保空间可写入）对于超大文件名，目前暂时没有设计解决方案，初步设想：维护一个回退偏移量管理这种边界问题

5. **压缩/解压时路径拼接细则**：
   - 读到文件标 0-目录进队等待处理（存完整路径），读到文件标 1-文件，按当前路径拼接并且交予数据加载模块。
   - 遍历完第一层一个目录记录的"子文件数量"后。继续处理队列中的目录，此时可能是第一层目录，也可能开启了第二层循环。
   - 逻辑根目录需要在压缩时忽略
   - 路径（原始、压缩输出路径）：要在 gui 层新增把 vector 传输给 HeaderLoader 模块的接口，不只是传给 HeaderWriter。以 std::filesystem::path 传输

**实际实现**：

`BinaryStandardLoader::headerLoaderIterator` 验证文件头，按分割标准读取、解密目录块，再交给 `EntryParser` 填充文件和目录队列。

## 4.3 压缩实现详解

1. 跳过逻辑根，但是要获取数目
2. 从 GUI 获得一个路径 vector。获取尾端目录/文件名-用于验证文件目录已经正确写入，验证通过后直接使用路径入队处理
3. 从预备压缩文件中读取一个 vector 目录块并解析信息
4. 主循环：
   - I:读取目录块中的信息
   - II:读取到文件则拼接后读取数据块并传给处理模块（需要把整个文件的数据完整传输两次，第一次构建编码树，第二次真处理，分别写两个函数，其一适配构建编码树这个特殊需求）,结束时对当前工作目录的 count--（依赖处理模块传回的结束信息）
   - III:读取到目录则拼接后存其 details 到队列备用，结束时对当前工作目录的 count--
   - count 减小到零后把目录 details 弹出
   - IV:按策略处理数据块，而后写入压缩文件，注意加密需要写入 iv 头
   - 当前文件的循环结束： 末尾按照分割标准分割写入一个编码表，并且回填 vector 中的偏移量（偏移位置已保存）
   - 启动下一个文件/目录的处理，如果 vector 目录块已经处理完，则再读取目录块
   - 外层循环：按策略处理 vector 目录块（加密），而后覆写在原位置减去 iv 头长度的位置上
   - 加密相关：文件目录和编码表，如果有加密，则是仅加密，不压缩的

## 4.4 解压缩实现详解

1. 获取文件头策略编号以及版本号，据此选择解压策略
2. 主循环：
   - 按偏移量逐个读取目录块，交由处理模块解密后回传，在内存中使用
   - 如果是目录：创建文件夹，并且入队其 details，按照队列的标准流程处理（同压缩实现过程）
   - 如果是文件：创建文件，读取压缩后，文件数据并且传给处理模块，回传后写入对应文件

## 4.5 核心类实现

### CompressionLoop

压缩流程控制器，负责文件遍历、分块处理、写入和进度回调。

### DecompressionLoop（v2.0.0 新增独立模块）

解压流程控制器，负责目录恢复、文件处理、数据块解码和进度回调。

### CompressionWorker-GUI版本专用

GUI 后台执行器，负责调用压缩/解压流程、取消和进度信号。

### HeaderWriter

按版本策略写入文件头和目录结构。

### BinaryStandardLoader

读取、解析或加密回填目录块，并维护文件和目录队列。

### DataLoader

按块读取文件，维护输入流、缓冲区和读取状态。

### DataExporter

写入压缩或解压数据，统计当前文件大小并回填偏移量。

### Heffman

Huffman 核心，负责频率统计、树和编码表生成、序列化、编码及解码。

### Aes

AES-128 核心，负责密钥派生、密钥扩展、CFB 加解密和密钥清理。

### NullCompression（v2.1.0 新增）

`ICompression` 空实现。使用 9 字节树桩保持 `[树块][数据块]` 格式，数据直接透传。

### NullEncryption（v2.1.0 新增）

`IEncryption` 空实现，加解密为恒等拷贝。

### StrategyFactory（v2.1.0 新增）

根据 `CompressionMode` 创建对应的压缩和加密模块。

**支持的策略**：

| 策略号 | 模式 | 压缩 | 加密 |
|--------|------|------|------|
| 0 | HuffmanAES | Huffman | AES |
| 1 | HuffmanOnly | Huffman | Null |
| 2 | AESOnly | Null | AES |
| 3 | PackOnly | Null | Null |

策略号写入 `Header.strategy`，解压时自动选择；工厂同时管理 AES 对象生命周期。

# 5. 并发与性能优化

## 5.1 性能优化

### 5.1.1 实测吞吐（v2.2.0 多线程流水线，HuffmanAES）

> 完整方法论与逐场景明细见 git 历史《性能报告-2026-09-07.md》（2026-09-07 收编入本节）。速度以吞吐量计——秒数只是单次事件的注脚。

对照旧版（串行主循环）与 v2.2.0，同机同输入（16 逻辑核 / NVMe / g++ -O2）：

| 场景 | 数据特征 | 旧版吞吐 | v2.2.0 吞吐 | 提升 |
|---|---|---|---|---|
| 正常文件 | 均 311KB/文件，4GiB 子集 | 19.1 MiB/s | **131.9 MiB/s** | **6.9×** |
| 长路径 | 均 75KB/文件，2.42GiB 全量，路径最深 267 字符 | 14.7 MiB/s | **52.6 MiB/s** | **3.6×** |
| 小文件极端 | 均 172B/文件，15 万文件子集 | 962 文件/s | **1,743 文件/s** | **1.8×** |

每压缩 1 GiB 的倒数视角：正常文件 53.6 s/GiB → **7.8 s/GiB**，长路径 69.6 s/GiB → **19.5 s/GiB**。新版全量参考：13.47GiB / 45,390 文件 106.5 MiB/s；25 万小文件 1,518 文件/s。解压仍串行：20~24 MiB/s（小文件场景 1,135 文件/s）。正确性：三个全量归档解压后文件数与字节数与源精确一致；非加密模式流水线产物与串行版逐字节相同（tool_archivebaseline 验收）。

方法要点：旧版限时子集（30 秒切片标定吞吐反推数据量，三场景三进程并行，单项 ≤4 分钟），新版独占机器串行跑同一批子集；旧版全量数字为线性外推。

原因分析：吞吐提升随文件变大单调放大——能摊到 N 核的只有压缩/加密计算段；目录枚举、逐文件 open/close、逐文件结算是串行端点，不随核数增长，是所有场景共享的地板。小文件场景 1.8× 中相当部分来自新版 CSP 句柄缓存（旧版每次 encrypt 都获取/释放系统加密句柄，小文件每文件两次），纯流水线贡献低于表观值。

### 5.1.2 优化方向（未实施）

- **解压并行化**：解压吞吐 20~24 MiB/s，与压缩侧收益不对称，优先级最高；
- **小文件端点优化**：调度合批（读线程一次持锁放一批 + 按空→非空转换合并唤醒；工人按字节预算批量取任务）——无竞争拿锁约 20~50ns、睡醒往返 5~20µs，差两三个数量级，要摊薄的是后者；
- **SIMD 指令加速**：AES-NI 可将 AES 提升 5~10 倍；AVX2 加速 Huffman 位操作与频率统计；
- **内存映射读取**（mmap / CreateFileMapping），省一次数据拷贝；
- ThreadSanitizer（WSL）数据竞争检查。

## 5.2 线程模型（已落地：三段压缩流水线，2026-09-07）

> 本节原为调研稿（通用线程池 v2 + WorkerEnv 草图），实施前先在 ThreadLab 原型上验证模型（5.2.2），落地时按验证结论简化为固定角色流水线；调研底稿与实施记录存于 git 历史《线程池调研与改造计划.md》。解压路径仍为串行。

### 5.2.1 总体架构（现行代码：Y_Manager/CompressionLoop.cpp 总指挥编排）

```
专职读线程 ──任务队列(SafeQueue)──> N 个计算工人 ──结果队列(SafeQueue)──> 专职写线程
      │                                                                    │
      └──────────── 全局 BufferPool（在途块上限 = 唯一背压点）──────────────┘
```

| 角色 | 职责 |
|---|---|
| 专职读线程 | 目录装载（BinaryStandardLoader 迭代 fileQueue）、借池块复制数据（DataLoader::getBlock 返回内部引用，必须复制）、分配全局递增序号、提交任务；进度回调与 GUI 取消只挂此线程；文件完成发结算消息；结束移交 takeBlockSpans() |
| 计算工人 ×N（N = hardware_concurrency，取不到退 4） | 开头各自 `createModules(mode, password)` 一份私有模块；压缩 + 两次加密；**零池调用**（见 5.2.4） |
| 专职写线程 | WriteSorter 按序号重排（区段连续性判据），DataExporter 纯追加写盘，攒 SizeFillEntry 表；首个任务异常按序重抛停刷；结果块写盘后归还池 |

设计原则：**有状态的阶段用专职线程，无状态的计算进对称工人池；读、写不做池任务**（读需要背压、写需要串行有序，进池会造成池内饥饿）；**背压点唯一落在缓冲池**——两级队列只流闭包与小对象、不设容量上限，内存峰值 = 池容量 × 块大小（容量 2×(N+2)，块大小 8MB+1KB 余量容纳加密 IV）。容量上限决定正确性（防内存膨胀），批量大小只决定性能（摊薄固定开销）——两个可调参数由此分清。

### 5.2.2 原型验证：ThreadLab（模型在落地前的实跑场所）

ThreadLab（D:\My_Docs\Tmp\cpp\ThreadLab）是独立的最小验证工程：不碰真实归档格式，用 100 个"包装盒"把三段流水线的每个机制实跑一遍。它的价值是把设计决策从纸面推理变成可执行验证，工程落地时逐项对照转换。

**组件与具体实现**（与 SFC 同名组件同源，此处描述 lab 原型）：

- `SafeQueue`（管程队列，66 行）：`std::queue` + `mutex` + `condition_variable` + `isDone` 四个私有成员；`push(T&&)` 锁内入队、**解锁后** notify_one（不抱着锁唤醒）；`waitPop(T&)` 谓词「非空 或 已结束」（析取），返回 bool——true 出货、false 即「空 且 已结束」（合取，退出信号）；`setDone()` 锁内置位、锁外 notify_all。
- `Y_flib::BufferPool`（对象池）：构造预分配 capacity 块，每块 `reserve(8MB)` 但**长度为 0**（不 memset、不 resize，出池后 assign/resize 填充不触发重分配）；空闲块为 LIFO 栈（栈顶复用缓存热块）；`acquire` 谓词「有空闲 或 已关」，关闭后抛异常（中止型关闭）；`release` 只清长度保留容量并唤醒一个借出者，池已关闭时静默弃块。
- `Pack`：`{uint64_t sequence, DataBlock data}`——data 就是从池借出的块本体，序号 + 块在阶段间全程移动语义转移，写盘后由分解者归还池。
- `WriteSorter`（按序刷盘缓冲）：`unordered_map<序号, Pack>` 缓冲 + 三个簿记值（`lastWrited` 已写前缀、`minSequence`/`maxSequence` 当前段界）。`canWrite(Pack&)` 入表并更新段界，回报连续性判据：`条数 == max-min+1`（段内无洞）**且** `lastWrited == min-1`（恰接已写前缀）；满足则驱动方逐序号 `takePack` 移动取出、写盘、还池，最后 `reset()` 推进前缀并清段界。
- `PipelineContext`：一轮的全部共享状态（两条队列 + 池 + 消费者剩余计数）包在一个类里，每轮新建、随轮析构，**零全局变量**——多轮运行互不残留。
- 三个线程函数：`producer` 按 1..N 编号，acquire → assign 装货 → push，结束后自行 setDone 上游队列；`consumer`×5 每线程一份私有 `mt19937`（模拟 100~1000ms 随机计算耗时）逐字节变换后 push 下游，**最后一个离开的消费者**经 atomic 剩余计数关闭下游队列；`decomposer` 用 WriteSorter 重组，逐盒追加写盘并 release 还池。
- 配置：100 盒 / 5 消费者 / 池容量 10（在途块上限）。验证结果：100 盒严格按序落盘、数据块全数归还、多轮重复无残留（2026-09-07 复跑确认）。

**落地到 SFC 的转换对照**：

| ThreadLab | SFC v2.2.0 | 变化与原因 |
|---|---|---|
| `SafeQueue<Pack>` 硬编码元素 | `SafeQueue<T>` 模板 ×2 实例 | 承载 BlockTask / PipelineMessage 两类消息；补上「结束后 push 拒绝」（lab 不拒绝，仅靠调用顺序单层保证） |
| `Pack{seq, data}` | `BlockTask` / `PipelineMessage`（kind 标签单结构） | 文件结算与任务异常也占序号随消息流转；元数据小对象不进池 |
| 每线程私有 `mt19937` | 每工人 `createModules` 私有模块 | 同一"线程私有工具"模式，换成真实算法模块 |
| `writeToDisk` 硬编码路径逐条开文件 | `DataExporter` 纯追加写归档 | 真实归档布局与块前缀 |
| `canWrite(Pack&)` 拷贝入表 | `canWrite(seq, T&&)` 移动入表 + `takeInOrder()` 整段取出 | 修掉每块一次整块拷贝；刷出编排（枚举期望区间、推进前缀）收进类内，调用方不再手搓 getSize/take/reset |
| 消费者剩余计数倒计时关下游、生产者自关上游 | 总指挥集中关闭（5.2.6） | 工人异常退出时倒计时永不归零，下游永久挂睡；集中关对错误路径安全 |

### 5.2.3 消息协议与序号规则（Y_Manager/PipelineMessages.h）

```
BlockTask       { sequence, inputData(池块,明文) }
PipelineMessage { sequence, kind: Block|Settlement,
                  encryptedMetadata(小,不进池), encryptedData(池块,密文), exception,
                  processedSizeOffset }
```

- 一个任务 = 一个 8MB 输入块，产两段输出（加密元数据块 + 加密数据块），写序与串行版一致，归档字节布局不变。
- **序号无洞由结构保证**：读端单线程按序分配，块与文件结算都占号、异常消息不跳号，队列排空契约不丢——最坏情形全部消息在写端汇合一次刷出（WriteSorter 连续性判据因此总能在收尾满足）。
- 空文件只有结算消息（不写任何字节），天然有序；槽偏移随结算直送写线程，无需对账单。

### 5.2.4 关键不变量：池块随消息走全链路（防死锁核心）

**读线程是池的唯一借出方，写线程是唯一归还方，工人全程不触碰池**：压缩产出先落工人私有缓冲，再以加密输出原地覆写池块（明文→密文），块所有权随消息移交写线程。依赖图无环，结构性无死锁。

反例存档：曾把工人写成"压缩完先还输入块、再从池借输出块"——被还的块被读线程抢走变成新任务占块（任务队列无界），池被"排队任务 + 不可按序刷出的乱序结果"占满时工人/写线程/读线程四方互等，永久 wedge；小文件任务快未踩中，AES 慢窗口必现。修复即恢复上述不变量，异常路径中块也照常随消息到写线程由唯一归还方统一还池。

### 5.2.5 共享对象的管程形态与唤醒机理（ThreadLab 问答定稿）

**管程**：一块被多线程共享的数据 + 一把互斥锁 + 条件变量 + 全部操作封装成一个对象，数据私有、操作是唯一访问路径、状态只在操作内持锁修改。本框架里需要管程形态的是**任务队列、结果队列、缓冲池**；反例是写线程的定序器（WriteSorter 簿记）——只被写线程自己访问，是单线程私有状态，不需要也不应该加锁。C++ 无语言级管程，用"类 + mutex + condition_variable"手动组装，信号语义是"通知即继续"：通知者通知完继续执行，被通知者自行持锁复查。

**谓词的保证粒度 = 一个临界区**：谓词为真是持锁判断的；`wait` 返回时锁仍在线程手里；所以"复查为真 → 在同一临界区内取出"原子相连，别人不可能在"判定有任务"与"取走任务"之间插入。它不保证谓词在未来持续为真——解锁后别人即可改状态。硬性要求：谓词读的共享状态必须由修改方在同一把锁内修改，否则是数据竞争，谓词不可信。

**三类唤醒错误的机制**（正确性拆在入睡与醒来两侧，机制不同）：

- **伪唤醒**：条件变量的契约允许唤醒多于实际需要（唤醒全部后多醒、实现合并唤醒），醒来时未必有对应状态变化——契约要求每次醒来持锁复查。Windows 几乎不产生无来由唤醒，但代码不能依赖平台。
- **唤醒陈旧**：共享队列上是对称竞争，锁仲裁"临界区谁先谁后"，不仲裁"这次唤醒对应的任务归谁"。时刻表：生产者入队并唤醒 A → 消费者 B 执行完上一任务先抢到锁、复查弹出该任务 → A 终于抢到锁、复查谓词为假、再睡。A 是为该任务被唤醒的，任务却在 A 抢到锁前被 B 取走——这是对称池的正常状态，醒后持锁复查正是为此。
- **丢失唤醒**：通知没有记忆，`notify_one` 调用时刻没有等待者即为空操作。它被消灭在**入睡侧**：`wait` 把"释放锁 + 登记等待者 + 睡眠"做成一个原子步骤，生产者要入队唤醒必须先拿锁，而拿锁的前提是消费者已完成登记——生产者能唤醒的那一刻，消费者必然已在等待列表上。（谓词挡的是醒来侧的前两类，不是这一类。）

**唤醒方向规则**：状态变真的那一方，唤醒正在等该状态的另一方。本设计队列无界、只有消费者一侧等待，唤醒单向（放数据方唤醒取数据方）；池的借出总量被容量封顶、归还必然发生，归还者不存在"等别人腾空位"，归还唤醒一个借出者即可。

**拿锁不是税**：一次无竞争的拿锁放锁约 20~50ns，睡醒往返约 5~20µs，差两三个数量级——入队每次拿锁从来不是瓶颈，要摊薄的是睡醒往返（见 5.1.2 合批）。

### 5.2.6 关闭协议（总指挥集中关）

关闭标记住在队列管程的成员里（与队列共用同一把锁），**不随任务结构体传递**——睡着的工人在任务之间不接收任何结构体，它与外界唯一的接触点是锁、锁保护的共享状态、条件变量的唤醒；"已关闭"要送进每个睡眠者，就必须住在这些接触点覆盖的共享状态里。关闭时有工人正在执行是正常状态，不是不健康的关闭。

收口顺序：join 读（取结算表与 takeBlockSpans）→ 关任务队列 → join 工人（排空契约：不打断执行中任务、不丢已入队任务）→ 关结果队列 → join 写 → CatalogFinalizer 收尾 → 关池。错误/取消路径同序收口后统一重抛首异常；未收尾的归档本就解不开（大小槽为 0、目录未加密），中断语义与串行版一致。ThreadLab 原型用"生产者自关上游 + 最后工人倒计时关下游"的分布式收口，工程版改为集中式：工人异常退出时倒计时永不归零，下游将永久挂睡。

### 5.2.7 模块并发安全性结论（调研定稿，实施采用"每工人一份实例"）

全部模块的不安全点都属于可变成员状态，不存在需要重写算法的模块；每工人一个实例即可全部消除（CFB 块内串行不影响——并行单位是 8MB 块，块间 IV 相互独立）。实施中未采用类型擦除的 WorkerEnv，工人线程开头直接 createModules 一次更简单。

| 模块 | 不安全点（可变成员状态） | 并发处理 |
|---|---|---|
| `Aes` | `iv`、`buffer` 每次 doAes 覆写 | 每工人一个实例；`w[44]` 与查表构造后只读，共享安全 |
| `Huffman` | freqTab/hashTab/treeRoot 被 compress/decompress 全程读写 | 每工人一个实例；每块独立树保证正确 |
| `DataLoader` | 内部缓冲被每次读取覆写，`getBlock()` 返回其引用 | 读线程持有；提交任务前复制进池块 |
| `DataExporter` | fstream + 写入顺序依赖 | 写线程独占 |
| `BinaryStandardLoader` | fileQueue、块缓冲、游标状态 | 读线程持有；takeBlockSpans() 结束时移交 |
| `HeaderWriter` | 仅建档阶段一次性使用 | 启动阶段串行，无并发问题 |
| `CatalogFinalizer` | 收尾专用 fstream | 流水线排空后总指挥串行调用 |
| `StandardsWriter`/`Locator`/`EncodingUtils` | 无状态静态/纯函数 | 安全 |
| GUI | — | 压缩已在独立 QThread，`m_stopRequested` 为 atomic，进度信号参数全为 Qt 内建类型（跨线程排队连接安全） |

# 6. 问题、安全与后续改进

## 6.1 已修复问题

1. **目录块边界产生空块**：分割前检查缓冲区是否有数据。
2. **Huffman 单字符树构建失败**：单字符固定编码为 `0`。
3. **LTO 构建异常**：使用 `-O3 -fno-lto`。
4. **GUI 中文路径乱码**：统一使用 UTF-8 路径转换。
5. **进度回调阻塞 UI**：进度信号节流并移除循环输出。
6. **内存持续增长**：复用预分配缓冲，必要位置使用 `swap()` 释放。
7. **部署体积过大**：使用 Qt 6.2.4 静态链接生成单 exe。

### 密钥管理方案设计

**实际实现**：密码经 SHA-256 后取前 16 字节作为密钥，析构时清零。

**当前实现**：AES-CFB；每个分割标准保存对应的随机 IV。

**当前状态**：未实现。可增加 HMAC，或改用 AES-GCM 等 AEAD 模式。
