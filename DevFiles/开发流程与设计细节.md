# 1. 用户需求与程序概览

## 1.1 用户需求

应用需要尽可能给用户提供自由的压缩选项。

- 加密：GUI 通过一个勾选器和一个列表选择器让用户选择。使用 AES-128，密码经 SHA-256 后取前 16 字节作为密钥。
- 多文件：支持将多个文件或目录压缩到单个 `.sy` 文件。
- 入口：提供 Qt GUI。

## 1.2 技术名词

- AES 加密：高级加密标准，对称性加密算法。本程序使用 AES-128，128 bit 密钥，10 轮处理。
- Huffman 编码：基于前缀码的无损压缩算法。基于自然语言重复性实现压缩。
- Qt：C++ 的 GUI 框架，跨平台兼容。
- 文件头：包含压缩文件基本信息的数据结构。
- 信号与槽：Qt 框架的核心思想，响应式 GUI 编程。
- 锁：控制临界区的变量，持有锁的线程可以进入临界区。
- 条件变量：核心为休眠队列，通过信号唤醒队列中的线程。
- 信号量：控制进入临界区线程的数量。
- 死锁：多个线程争抢锁的形式构成单向环图的状况。造成线程永久的休眠。
- 系统调用：由操作系统提供给应用程序的接口。通常是受限操作，由操作系统执行。

# 2. 程序初步设计

## 2.1 程序结构及要点

### Compress/Decompress_System

- 负责压缩与解压。
- 核心类：`CompressionLoop`、`DecompressionLoop`
- 调用 Huffman 模块和 AES 模块

### Encryption/Decryption_System

- 负责加密与解密工作。
- 核心类：`Aes`
- 支持 SHA-256 密钥派生

### BufferPool

- 缓存以上两者的输出
- 充当可接受线程管理器动态调度的对象
- 每个线程组独立使用一个缓存池
- 加入大小限制和溢出处理机制
- 充当接收输入并缓存/主动抛出的作用
- 数据通过 `Y_flib::DataBlock` 同步传递，它是 `std::vector<unsigned char>` 的类型别名

## 2.2 模块设计

### Encryption 加密模块设计

1. 密钥 hash 处理
   
   用户输入任意长度的密码后，程序调用 SHA-256 算法对密码进行哈希处理，生成 32 字节的哈希值，然后取前 16 字节作为 AES-128 的实际密钥。这样做的好处是支持任意长度密码，同时保证密钥长度符合 AES 要求。

2. 加密模式
   
   AES-128-CTR，密钥流由 ECB 批量加密计数器块生成。CTR 属流模式，不需要填充，数据长度保持不变。

3. 缓存池
   
   使用 `Y_flib::DataBlock` 作为数据缓冲，这是一个动态数组，可以自动扩展和管理内存。

### Compression 压缩模块设计

1. 频率统计
   
   遍历数据块中的每个字节，统计 0-255 各个字节值出现的次数。

2. 树构建
   
   使用最小堆（优先队列）数据结构，每次从堆中取出频率最小的两个节点，合并为一个新节点，新节点的频率为两者之和。重复此过程直到只剩一个节点，即为 Huffman 树的根节点。

3. 编码
   
   由树生成 canonical 前缀码，写入平坦的 256 项编码表，再以 64 位位缓冲按符号批量合并。
   
4. 解码
   
   把码长表还原为 canonical 码并构建 12 位查找表，每符号一次查表；码长超过 12 位的符号回退为逐位还原。

### 文件模块设计

1. 状态检测器：检测加密状态（Y/N）。监控文件压缩进度。通过 `Header.strategy` 记录处理策略。

2. 文件信息读取器：将文件的整个文件头读取到程序缓存中，并进行相关检查。监控文件解压进度。由 `BinaryStandardLoader` 读取文件头和目录块。

- 关于数据块类：

`Y_flib::DataBlock` 是 `std::vector<unsigned char>` 的类型别名。

- 偏移量记录方式和相关规则

  - 维护：在文件头中存储数据文件的文件名初始大小，解压时逐步递减，直至字节数不足。
  - 压缩时动态维护已压缩文件的大小，待数据块抛出进程结束信号时写入文件头中预留好的偏移量的数据上。
  - 偏移量使用 `uint64_t`，写入时维护并回填预留位置。

### GUI 模块设计

目标：GUI 只负责交互与调度，压缩/解压核心逻辑继续复用 `Y_Manager` 与 `CompressorFileSystem`，避免形成一套 CLI、一套 GUI 的重复实现。

- `MainWindow` 管理界面和后台 `QThread`，`CompressionWorker` 调用核心流程并回传进度。
- 支持 `HuffmanAES`、`HuffmanOnly`、`AESOnly`、`PackOnly`，解压时按 `Header.strategy` 自动选择。
- 支持压缩/解压分页、拖放、取消和界面本地化。
- 路径统一经 `EncodingUtils` 在 UTF-8 与 `std::filesystem::path` 间转换。
- 使用 Qt 6.2.4 及其匹配的 MinGW，开发使用动态部署，发布使用静态单 exe。

# 3. 文件格式与底层细节

## 3.1 技术整合与文件格式

主要技术：

- 加密：aes-128，128 bit 密钥，十轮处理。
- 压缩：huffman，基于自然语言重复性的压缩算法
- 控制：线程与线程、模块与缓存池之间的组合与调度

### 文件格式设计

```
┌─────────────────────────────────────────────────────────┐
│                      .sy 文件结构                        │
├─────────────────────────────────────────────────────────┤
│ [文件头 19字节]                                          │
│ ├─ magicNum_1 (4B)  : 0xDEADBEEF 文件标识               │
│ ├─ strategy (1B)    : 压缩策略号                        │
│ ├─ version (1B)     : 版本号                            │
│ ├─ headerOffset (1B): 文件头偏移（保留）                │
│ ├─ directoryOffset(8B): 目录块起始偏移量                │
│ └─ magicNum_2 (4B)  : 0xDEADBEEF 校验标识               │
├─────────────────────────────────────────────────────────┤
│ [目录块区域]                                             │
│ ├─ [分割标准 25B] → blockSize + IV                      │
│ ├─ [目录块数据] → 文件/目录标准（AES-CTR 加密）         │
│ ├─ [分割标准 25B]                                       │
│ ├─ [目录块数据]                                         │
│ └─ ...                                                  │
├─────────────────────────────────────────────────────────┤
│ [数据区]                                                 │
│ ├─ [分割标准 25B] → blockSize + IV                      │
│ ├─ [码长表 258B] → AES-CTR 加密，无填充                 │
│ ├─ [分割标准 25B]                                       │
│ ├─ [压缩数据] → AES-CTR 加密 + 末尾1字节有效位数        │
│ └─ ...（重复以上结构直到文件结束）                      │
└─────────────────────────────────────────────────────────┘
```

每个数据块都具有自己的码长表，且在数据区的末尾添加了一字节标识符，以区分 Huffman 填充与有效数据。

### 文件头结构（Header）

| 字段 | 类型 | 大小 | 说明 |
|------|------|------|------|
| magicNum_1 | uint32_t | 4字节 | 魔数 `0xDEADBEEF`，文件标识 |
| strategy | uint8_t | 1字节 | 压缩策略号（当前为 0） |
| version | uint8_t | 1字节 | 版本号（当前为 3） |
| headerOffset | uint8_t | 1字节 | 文件头偏移（保留） |
| directoryOffset | uint64_t | 8字节 | 目录块起始偏移量 |
| magicNum_2 | uint32_t | 4字节 | 魔数 `0xDEADBEEF`，校验标识 |
| 总计 | | 19字节 | |

### 目录块结构

目录块由多个"标准"（Standard）组成，每个标准以 `FlagType` 标识符开头：

### 文件标准（FlagType::File = 1）

| 字段 | 类型 | 大小 | 说明 |
|------|------|------|------|
| flag | uint8_t | 1字节 | 标识符 `1` |

| name | char[] | 变长 | UTF-8 编码文件名 |
| originalSize | uint64_t | 8字节 | 原始文件大小 |

### 目录标准（FlagType::Directory = 0）

| 字段 | 类型 | 大小 | 说明 |
|------|------|------|------|
| flag | uint8_t | 1字节 | 标识符 `0` |
| nameSize | uint32_t | 4字节 | 目录名长度 |
| name | char[] | 变长 | UTF-8 编码目录名 |
| childCount | uint32_t | 4字节 | 子元素数量 |
| 基础大小 | | 9字节 | 不含目录名 |

### 分割标准（FlagType::Separated = 2）

| 字段 | 类型 | 大小 | 说明 |
|------|------|------|------|
| flag | uint8_t | 1字节 | 标识符 `2` |
| blockSize | uint64_t | 8字节 | 数据块大小 |
| iv | uint8_t[16] | 16字节 | AES 加密初始化向量 |
| 总计 | | 25字节 | |

### 逻辑根目录标准（FlagType::LogicalRoot = 3）

| 字段 | 类型 | 大小 | 说明 |
|------|------|------|------|
| flag | uint8_t | 1字节 | 标识符 `3` |
| nameSize | uint32_t | 4字节 | 根目录名长度 |
| name | char[] | 变长 | UTF-8 编码根目录名 |
| childCount | uint32_t | 4字节 | 子元素数量 |

### Windows 链接标准（FlagType = 4/5/6）

| 字段 | 类型 | 大小 | 说明 |
|------|------|------|------|
| flag | uint8_t | 1字节 | `4`=文件符号链接，`5`=目录符号链接，`6`=Junction |
| nameSize | uint32_t | 4字节 | 链接名长度 |
| targetSize | uint32_t | 4字节 | 目标路径长度 |
| name | char[] | 变长 | UTF-8 编码链接名 |
| target | char[] | 变长 | UTF-8 编码、链接自身记录的原始目标路径 |
| 基础大小 | | 9字节 | 不含变长字段 |

压缩扫描遇到 Windows 符号链接或 Junction 时，仅读取重解析点自身并写入上述元数据。相对目标保持相对形式，绝对目标保持绝对形式，目标位于归档根目录之外、目标缺失或链接之间形成循环均照常归档。解压时先恢复普通文件和目录，再按记录的目标字符串重建链接；目标在另一台机器上缺失时，恢复结果是正常的悬空链接。

### 数据区结构

每个文件的数据由多个数据块组成，每个数据块结构如下：

```
[分割标准 25字节]
├─ flag: 2
├─ blockSize: 码长表大小
└─ iv: AES 加密 IV（若未加密则为全零）

[码长表]
└─ AES-CTR 模式加密的 'L' + 最大码长 + 256 项码长（无填充）

[分割标准 25字节]
├─ flag: 2
├─ blockSize: 压缩数据大小
└─ iv: AES 加密 IV（若未加密则为全零）

[压缩数据]
├─ AES-CTR 模式加密的 Huffman 编码数据（无填充）
└─ 末尾一字节：有效数据位数标识
```

加密说明：采用 AES-CTR 流模式加密，每个数据块前置 16 字节随机 IV，密文长度与明文相同。这样做使数据区长度不变，避免填充位导致偏移量回填计算复杂化、截断误判与解析攻击。

### 目录块加密

当启用加密时，目录块会被加密：

1. 压缩时：目录信息写入完成后，读取整个目录块，AES 加密后覆写回原位置
2. 每个分割标准中的 `iv` 字段存储该块的加密初始化向量
3. 解压时：读取目录块，检查 `iv` 是否非零，若非零则先解密再解析

# 4. 当前实现

## 4.1 算法与文件处理

### AES 加密实现

- 密码经 SHA-256 后取前 16 字节作为 AES-128 密钥。
- 加密与解密由 Windows CNG 提供，算法为 AES-128-CTR。CNG 的原生 CTR 不可用，密钥流由 ECB 模式批量加密计数器块生成；计数器为 128 位大端。
- 每个数据块前置 16 字节随机 IV，由 `BCryptGenRandom` 生成。
- `Aes` 实例持有 CNG 算法句柄与密钥句柄，不可复制，按模块私有使用。析构时清零密钥副本并释放句柄。

### Huffman 压缩实现

- 统计 256 种字节频率，通过最小堆构建 Huffman 树。
- 由树生成 canonical 前缀码，存入平坦的 256 项编码表；编码以 64 位位缓冲按符号批量合并输出。
- 码长表序列化为 `'L'` + 最大码长 + 256 项码长，共 258 字节，取代整树序列化。
- 解码把码长表还原为 canonical 码，并构建 12 位查找表，每符号一次查表；码长超过 12 位的符号回退为逐位还原。
- 单字符数据块固定使用编码 `0`。

### 文件头实现

1. 记录文件头和数据块的偏移量
2. 记录压缩方案：加密方式/有无加密、压缩方式
3. 在文件头记录文件的目录结构、偏移量：目录结构使用前缀索引，偏移量单独在文件名后存储，为每个节点预留 2\*8 字节，分别存储文件压缩前后大小
4. 动态获取的偏移量在接到结束信号后从缓冲区写入文件，以此实现实时存储

   读取文件目录之后直接在文件头中逐个处理对应文件，服务于数据偏移量更新，并且在预留好的位置修改压缩后大小，不影响数据区写入数据。至此，实现无临时文件的方案已经完善。

### 文件信息存储标准

- 文件标为数值 `0`：为目录。需要写入：`|4B 第一级文件数量|`
- 文件标为数值 `1`：为文件。需要写入：`|8B 原文件大小|8B 压缩后偏移位|`。其中压缩大小暂时作为占位区。
- 文件标为数值 `2`：为分割偏移量，是为加密/分块特化的标签。写入 `|1B 标识符||8B 偏移量||16B iv 加密头|`。如果读到偏移量为零，说明此时已经写入到最后一个不足 8MB 的块，按目录的残余偏移量来读取，包含只有一块的情况；AES 的加密头会写入到预留位置
- 文件标为数值 `3`：为逻辑根目录标记，与普通目录存储仅有标识符不同
- 文件标识符为数值 `4`、`5`、`6`：分别为 Windows 文件符号链接、目录符号链接和 Junction。存储标准为 `|文件标|4B 文件名长度|4B 目标路径长度|文件名|原始目标路径|`。扫描时不进入、不解析链接目标，解压完成普通条目后直接按记录创建链接

`FlagType` 底层为 `uint8_t`，定义 `Directory(0)`、`File(1)`、`Separated(2)`、`LogicalRoot(3)`、`SymbolicLinkFile(4)`、`SymbolicLinkDirectory(5)`、`Junction(6)`。本项目实现 Windows 重解析点语义，基础大小见第 3 章格式表。

### 压缩前运行流程

- 0. 文件头开始与结束均需要写入魔数 `0xDEADBEEF`。
- 1. 目录：读取后写入对应的存储标准，并且在缓冲区中缓存一个文件数量。
- 2. 文件：读取后写入对应的存储标准
- 3. 搜索方案：采用 BFS。

  I：如果搜索到文件，直接写入。如果搜索到目录，进入该目录并且记录其中第二级文件数量以及该目录的完整路径到队列备用，并且按标准写入文件。

  II：记录完数量后返回，继续搜索第一级目录，重复操作 I，直到第一级搜索完成。

  III：处理队列，接着按照队列已存储的路径打开下一级目录，以先前获取的第二级文件数量及其所在目录的路径，按顺序读写对应的文件数据，直至文件数量耗尽为止。

  IV：重复上述操作直到读取完成。以上 I~III 解决了解压文件时如何按照顺序读取文件及其目录的问题。

  V：特别地，可以为目标文件提供一个逻辑根目录，以便始终遵循如上顺序读写数据，或者单独存储根目录下的子文件/目录数量。

  VI：文件头开始为写入文件头偏移量预留位置，文件头写入完毕后更新这个偏移量

  VII：如果需要加密，则按照偏移量在原内容上进行覆写

`EntryProcessor` 使用 BFS 扫描目录，写入文件或目录标准，并按 16KB 分割目录数据。偏移量通过 `seekg/seekp` 定位，写入位置由 `tempOffset` 同步维护，文件完成后回填大小。

### 文件头信息获取

1. 通用部分：
   - I：打开文件直接读取魔数，并且按照文件头方案读取策略等数据，如文件头以及文件目录的偏移量
   - II：定位到文件目录起始位置，根据分隔符将文件目录信息按块读进内存中处理
   - III：读取完文件信息/压缩后数据之后，记录此处的偏移量以便下一次处理时直接定位

2. 压缩时的信息获取：
   - 需要获取并且拼接文件的路径，通过某种传输方式发送给压缩模块处理。
   - 需要在获取到数据块结束标志时写入末尾偏移量，统一以当前文件大小存储，并且在循环中更新下一次起始位置为上一次末尾偏移量
   - 加密时确保数据块一次性处理完之后再交予写入程序写入文件中

3. 普通解压时的信息获取：
   - I：对于文件，获取其在数据区的偏移量并且定位到数据区对应的位置读取数据
   - II：对于文件夹，获取它携带的子文件数量信息并且记录到"下一层文件数量"，同时创建文件夹以及其 details 信息类对象，并将对象存入到队列中备用
   - III：按照以上方式读取数据直到耗尽当前目录的"文件数量"。根目录以及多文件根目录的边界情况使用加入逻辑根节点的方式解决
   - IV：循环以上操作，并且注意比对此时的读取位置与文件头中记录的文件目录偏移量。

4. 解压时数据获取：
   - 对于被加密的数据块：按偏移量分割，分块读取数据，解密后存储在内存中
   - 加密后的目录需要被读取到内存后经过解密处理传回文件处理模块使用
   - 内存中保留拼接好的路径，抛弃已处理完的文件目录数据，动态数组配合 `clear` 恢复 size=0，并 `resize` 确保空间可写入

5. 压缩/解压时路径拼接细则：
   - 读到文件标 0 目录进队等待处理并存储完整路径；读到文件标 1 文件，按当前路径拼接并且交予数据加载模块。
   - 遍历完第一层一个目录记录的"子文件数量"后，继续处理队列中的目录，此时可能是第一层目录，也可能开启了第二层循环。
   - 逻辑根目录在压缩时忽略
   - 路径以 `std::filesystem::path` 在 GUI 层与 HeaderLoader 模块之间传输

`BinaryStandardLoader::headerLoaderIterator` 验证文件头，按分割标准读取、解密目录块，再交给 `EntryParser` 填充文件和目录队列。

## 4.2 程序的运行流程

1. 用户选择操作模式（压缩/解压）
2. 选择输入文件和输出路径
3. 输入必要参数（如密码）
4. 初始化处理模块（HeaderWriter/HeaderLoader, Huffman, Aes）
5. 文件分块进入处理流水线
6. 加密/压缩顺序处理
7. 结果写入输出文件
8. 错误处理和日志记录
9. 内存清理和资源释放

CLI 收集参数后调用 `CompressionLoop` 或 `DecompressionLoop`；GUI 由 `CompressionWorker` 在后台 `QThread` 中调用相同核心流程，并支持进度显示和取消。

## 4.3 压缩实现详解

1. 跳过逻辑根，但是要获取数目
2. 从 GUI 获得一个路径 vector。获取尾端目录/文件名，用于验证文件目录已经正确写入，验证通过后直接使用路径入队处理
3. 从预备压缩文件中读取一个 vector 目录块并解析信息
4. 主循环：
   - I：读取目录块中的信息
   - II：读取到文件则拼接后读取数据块并传给处理模块，结束时对当前工作目录的 count--
   - III：读取到目录则拼接后存其 details 到队列备用，结束时对当前工作目录的 count--
   - count 减小到零后把目录 details 弹出
   - IV：按策略处理数据块，而后写入压缩文件，加密需要写入 iv 头
   - 当前文件的循环结束：末尾按照分割标准分割写入一个编码表，并且回填 vector 中的偏移量
   - 启动下一个文件/目录的处理，如果 vector 目录块已经处理完，则再读取目录块
   - 外层循环：按策略处理 vector 目录块（加密），而后覆写在原位置减去 iv 头长度的位置上
   - 加密相关：文件目录和编码表如果有加密，则仅加密，不压缩

## 4.4 解压缩实现详解

1. 获取文件头策略编号以及版本号，据此选择解压策略
2. 主循环：
   - 按偏移量逐个读取目录块，交由处理模块解密后回传，在内存中使用
   - 如果是目录：创建文件夹，并且入队其 details，按照队列的标准流程处理
   - 如果是文件：创建文件，读取压缩后文件数据并且传给处理模块，回传后写入对应文件

# 5. 并发与性能优化

## 5.1 性能优化

压缩与解压整体吞吐 254.3 与 325.1 MiB/s，对 13.47 GiB / 45,390 文件的测试数据实测。各项优化的完整数据、版本演进与瓶颈分析见 [《性能报告》](性能报告.md)。

各项优化的通用判据与方法论（三条判据、五个审计、决策树、跨语言映射、反模式清单、瓶颈判定法）单独整理为 [《性能优化通用方法论》](性能优化通用方法论.md)，接手新模块时可直接对照。

## 5.2 线程模型

### 5.2.1 总体架构

```
专职读线程 ──任务队列(SafeQueue)──> N 个计算工人 ──结果队列(SafeQueue)──> 专职写线程
      │                                                                    │
      └──────────── 全局 BufferPool（背压）──────────────┘
```

| 角色 | 职责 |
|---|---|
| 专职读线程 | 目录装载（BinaryStandardLoader 迭代 fileQueue）、借池块复制数据、分配全局递增序号、提交任务，进度回调与 GUI 取消只挂此线程，文件完成发结算消息，结束移交 takeBlockSpans() 做收尾处理 |
| 计算工人 N = hardware_concurrency 或 4 | 开头各自 `createModules(mode, password)` 一份私有模块，压缩 + 两次加密 |
| 专职写线程 | WriteSorter 按序号重排（区段连续性判据），DataExporter 纯追加写盘，攒 SizeFillEntry 表，首个任务异常按序重抛停刷，结果块写盘后归还池 |

### 5.2.2 并发组件

- `SafeQueue`：`std::queue` + `mutex` + `condition_variable` + `isDone` 四个私有成员，`push(T&&)` 锁内入队、解锁后 notify_one，避免持锁唤醒；`waitPop(T&)` 谓词为非空或已结束，返回 bool，true 出货、false 即空且已结束；`setDone()` 设置 close 信号并配合 notify_all 让等待线程同步退出。
- `Y_flib::BufferPool`：构造预分配 capacity 块，每块 `reserve(8MB)` 但长度为 0，不 memset、不 resize，出池后 assign/resize 填充不触发重分配；空闲块为 LIFO 栈，栈顶复用缓存热块；`acquire` 谓词为「有空闲 或 已关」，关闭后抛异常，属中止型关闭；`release` 只清长度保留容量并唤醒一个借出者，池已关闭时静默弃块。
- `WriteSorter`：`unordered_map<序号, Pack>` 缓冲加三个簿记值，即 `lastWrited` 已写前缀、`minSequence`/`maxSequence` 当前段界。`canWrite(Pack&)` 入表并更新段界，回报连续性判据：条数等于 max-min+1 且 lastWrited 等于 min-1，满足则驱动方逐序号 `takePack` 移动取出、写盘、还池，最后 `reset()` 推进前缀并清段界。

### 5.2.3 消息与序号规则（Y_Manager/PipelineMessages.h）

```
BlockTask       { sequence, inputData(池块,明文) }
PipelineMessage { sequence, kind: Block|Settlement,
                  encryptedMetadata(小,池外分配), encryptedData(池块,密文), exception,
                  processedSizeOffset }
```

一个任务 = 一个 8MB 输入块，产两段输出（加密元数据块 + 加密数据块），写序与归档字节布局均与串行版一致。

序号全局递增，由读线程单线程分配；块与文件界消息都占号、异常消息不跳号。序号无洞由结构保证：读端按序分配、工人每任务必产出、队列排空契约不丢。这是写线程 WriteSorter 区段连续性判据成立的前提，最坏情形是全部消息在写端汇合一次刷出。

池块随消息走全链路：读线程是唯一借出方，写线程是唯一归还方，工人零池调用。压缩侧以加密输出原地覆写明文输入，解压侧以解压输出原地覆写密文输入，块的所有权随消息移交写线程。

### 5.2.4 共享对象的管程形态与唤醒机理

管程：一块被多线程共享的数据 + 一把互斥锁 + 条件变量 + 全部操作封装成一个对象，数据私有、操作是唯一访问路径、状态只在操作内持锁修改。本框架里采用管程形态的是任务队列、结果队列、缓冲池；写线程的定序器仅被写线程自己访问，是单线程私有状态，免锁。C++ 以"类 + mutex + condition_variable"手动组装管程，信号语义是"通知即继续"：通知者通知完继续执行，被通知者自行持锁复查。

谓词的保证粒度 = 一个临界区：谓词为真是持锁判断的，`wait` 返回时锁仍在线程手里，所以"复查为真 → 在同一临界区内取出"原子相连，别人不可能在"判定有任务"与"取走任务"之间插入。谓词的有效性止于当前临界区，解锁后其他线程即可修改状态。硬性要求：谓词读的共享状态必须由修改方在同一把锁内修改，否则是数据竞争，谓词不可信。

三类唤醒错误的机制：

- 伪唤醒：条件变量的契约允许唤醒多于实际需要，唤醒全部后多醒、实现合并唤醒，醒来时未必有对应状态变化，契约要求每次醒来持锁复查。Windows 实现很少出现无来由唤醒，代码仍按契约持锁复查，保持平台无关。
- 唤醒陈旧：共享队列上是对称竞争，锁仲裁"临界区谁先谁后"，不仲裁"这次唤醒对应的任务归谁"。生产者入队并唤醒 A，消费者 B 执行完上一任务先抢到锁、复查弹出该任务，A 终于抢到锁、复查谓词为假、再睡。A 是为该任务被唤醒的，任务在 A 抢到锁前已被 B 取走，这是对称竞争的正常状态，醒后持锁复查正是为此。
- 丢失唤醒：通知没有记忆，`notify_one` 调用时刻没有等待者即为空操作。它被消灭在入睡侧：`wait` 把"释放锁 + 登记等待者 + 睡眠"做成一个原子步骤，生产者要入队唤醒必须先拿锁，而拿锁的前提是消费者已完成登记，生产者能唤醒的那一刻，消费者必然已在等待列表上。

唤醒方向规则：状态变真的那一方，唤醒正在等该状态的另一方。队列无界、只有消费者一侧等待，唤醒单向，放数据方唤醒取数据方；池的借出总量被容量封顶、归还必然发生，归还方仅做还块并唤醒一个借出者。

### 5.2.5 关闭

关闭标志存放在队列管程的成员里，与队列共用同一把锁，不随任务结构体传递。睡着的工人在任务之间不接收任何结构体，它与外界唯一的接触点是锁、锁保护的共享状态、条件变量的唤醒。

收口顺序：join 读，取结算表与 takeBlockSpans → 关任务队列 → join 工人，此时排空契约生效，不打断执行中任务也不丢已入队任务 → 关结果队列 → join 写 → CatalogFinalizer 收尾 → 关池。错误/取消路径同序收口后统一重抛首异常；中断的归档缺少收尾信息，大小槽为 0、目录未加密，属无效归档。

### 5.2.6 模块并发的解决方案：每工人一份实例

全部模块的不安全点都属于可变成员状态，每工人一份实例即可全部消除；AES 的 CTR 密钥流块内串行，并行单位是 8MB 块，块间 IV 相互独立。

### 5.2.7 解压流水线（与压缩侧同构复用）

解压侧复用压缩侧的并发组件与约定（SafeQueue ×2、WriteSorter、BufferPool、集中关闭、每工人私有模块），消息协议与读写语义按解压定制：

- 读线程：独占 BinaryStandardLoader 与数据区专用 ifstream，前者负责目录解析与目录区解密，使用自建模块实例。loader 的 restartLoader 会整体换流，目录区与数据区各持一条流，数据区从 directoryOffset 起纯顺序读、零 seek，文件边界按 fileQueue 顺序 + compressedSize 记账切分，与串行同逻辑，免去 tellg 链式推导。目录创建留在读线程，先于写线程落文件。
- FileStart 消息：每文件首块之前占序号，空文件只有它。写线程按序见到即结算上一文件、createFile、开新 DataExporter。这一"文件界占号"设计与压缩侧 Settlement 对称。
- 每块输出上限预计算：任务携带 `expectedOriginal = min(BUFFER_SIZE, originalSize − 已产字节)`，与串行 running-remaining 数学等价。压缩按 8MB 切块，非末块剩余 ≥8MB 且输出 ≤8MB，末块即精确尾长。这把串行的跨块累计状态拆成了无依赖的每任务参数，是解压能按块并行的关键。
- 工人：两次解密落私有缓冲，解压输出原地覆写池块，密文变明文。输出块先 `clear()` 再解压，因为池块此刻装着密文，decompress 的输出语义保留目标缓冲原有内容。
- 写线程：WriteSorter 定序 → FileStart 开关文件 / Block 追加写 + 还池，排空后由总指挥串行执行 processLinks，链接严格最后，目标可能是刚还原的文件。

# 6. 问题、安全与后续改进

## 6.1 AES 安全性

### 密钥管理方案

密码经 SHA-256 后取前 16 字节作为密钥，析构时清零。加密使用 AES-128-CTR，每个数据块前置 16 字节随机 IV，由 `BCryptGenRandom` 生成。

### 加密模式选择

AES-CTR 属流模式，密文长度与明文相同，无需填充。密钥流由 ECB 批量加密计数器块生成，直接走 CPU 的 AES-NI 硬件指令；容器内不保留自研的 AES 轮函数实现，因而也不存在软件后备路径，缺少 AES-NI 时由 CNG 自身回退。

## 6.2 数据完整性

后续方向是为数据块引入校验和，可选 CRC32 或 SHA-256，在解压后校验；同时为防篡改引入 HMAC，或改用 AES-GCM 等 AEAD 模式，把完整性保证并入加密本身。

## 6.3 系统安全

### 内存敏感数据清理

AES 析构时使用 `SecureZeroMemory` 清零主密钥副本，不可被编译器优化掉。
