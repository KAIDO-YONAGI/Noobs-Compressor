# 多 Agent 工作流指南

## 路由

按任务词、目标路径、运行资源与预期产物路由。任务描述只用来定位分类；具体操作
规则来自该分类的 Guide/Design。一个任务同时涉及多个业务时，进入每个受影响的
业务根，分别读取并分别记录。

判定顺序：

1. 这个任务要读或改哪些路径？路径落在哪个业务根的资源范围内。
2. 任务词是否命中某个 Router 的「任务线索」表。
3. 是否一稿改动就跨越了多个业务根（例如同时改格式与流水线）。

## 业务根

优先复用已有分类。新建顶级分类、修改工作区级规则，必须先获得用户确认。
每个业务根至少包含 `Router.md` 与 `DeveloperLog.md`。

本项目的业务根划分与理由记在 `DeveloperLog.md` 的初始化条目里，不要在别处重复。

## 层级深度

工作流根以下最多五层。将出现第六层时，依次考虑：把可独立演进的子类提升为业务根、
合并语义重复的父子层、用 Router 表格或标签替代目录。

当前结构只有两层（业务根 / 文档），远未触及限制。

## 维护

只有成功且实质影响某个业务的任务，才为该业务根的计数加一。失败、取消、租约登记、
只读调查与纯文档维护都不计数。到达 `5/5` 时，复查任务证据与项目实际状态，更新权威
文档或记录 `reviewed-no-change`，然后归零。

`DeveloperLog.md` 不自动裁剪历史。仅当用户明确确认某条记录冗余或过时后，才删除该条。

## 并发资源

- `workflow:<业务根>` 只在写该业务的 Router/Log 时短暂取得。
- `workflow:root` 只在调整根结构时取得。
- 构建、测试与运行统一用 `pipeline:BuildPublishRun` 作为全局屏障，具体命令见
  `Project_Validation_Guide.md`。
