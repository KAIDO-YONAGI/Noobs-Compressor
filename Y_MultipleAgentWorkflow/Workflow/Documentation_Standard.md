# SFC 文档撰写标准

文档 ID：`WF-DOC-STANDARD`  
状态：`Active`  
维护计数：`不计数`  
最后更新：`2026-10-26`

本文件是所有权威文档的**唯一**写作规则。各业务根 Guide 只写项目事实，不再重复本条。

---

## 1. 时态：只写当前状态

全文用现在时陈述此刻的事实，读起来像一份规格书，而不是一份履历。

| 该写 | 不该写 |
|---|---|
| 「密钥由口令经 SHA-256 派生。」 | 「密钥派生曾经用 MD5，后来改成了 SHA-256。」 |
| 「解压时先恢复目录，再重建链接。」 | 「以前是先建链接，现已调整为先恢复目录。」 |
| 「工人数默认取 CPU 逻辑核数。」 | 「v2.1 起工人数改为取逻辑核数。」 |
| 「归档格式版本为 3。」 | 「格式版本从 1 演进到 2，再到 3。」 |

版本号、字段取值、常量名都是当前事实，可以写；它们怎么变来的不写。

## 2. 不存在的、已过时的，直接不提

文档只描述当前存在的东西。缺失的功能、放弃的方案、别的文档写错的地方，都不占篇幅。

- 不写「尚未实现」「暂不支持」「未测试」「待补充」「后续计划」「暂时保留」。
- 不写「已知偏差」「旧文档的表述已过时」「此处需要纠正」。
- 需要表达某个能力不存在时，用一句正面的事实句，例如「本工具只提供静态数据机密性」，
  而不是「本工具没有完整性校验，该功能尚未实现」。

## 3. 不写版本变更记录与修改记录

文档内不出现以下小节：修订记录、更新日志、变更历史、版本演进、补丁说明、
「本次修改了什么」。

文档头的 `最后更新` 是元数据，属于结构要求，保留。除此之外不出现任何过程性叙述。

## 4. 不用括号塞解释

括号只允许用于三种情况：缩写全称、单位、代码标识符。

| 该写 | 不该写 |
|---|---|
| 「采用 CTR 模式，密文与明文等长。」 | 「采用 CTR 模式（即计数器模式，长度不变的那种）」。 |
| 「每个工人一份实例。」 | 「每个工人一份实例（因为轮密钥是可变的）」。 |
| 「块大小 8 MB。」 | 「块大小 8 MB（足够大又不会太占内存）」。 |

需要交代原因时，直接写成一句正文，放在对应断言之后。

## 5. 少用否定与转折

能正面陈述就不要用「不是……而是……」「并不」「并非」「与其说……不如说」这类句式。
一句话里最多出现一层转折。连续两句否定句式必须改写。

## 6. 必填文档头

每篇文档前 4 行固定为：

```text
文档 ID：`<ID>`
状态：`<Active|Proposal|Reference|Archived>`
维护计数：`<n>/5` 或 `不计数`
最后更新：`<YYYY-MM-DD>`
```

业务权威文档一律 `Active`。`Proposal` 只用于单独成篇的未实施方案，且不得出现在业务根的
权威链上。

## 7. 证据规则

1. 关于代码行为、字段宽度、常量取值、调用关系、线程归属的断言，必须能对应到本仓库的
   实际内容。
2. 优先给出短证据：文件路径与行号、常量名、类型名。不必逐句标注，关键结论必须有据。
3. 无法从代码确认的内容直接删掉，不要留「待核实」。
4. 性能数字必须注明测量条件与来源。没有测量条件支撑的数字不写。

## 8. 语言与术语

- 正文用简体中文。代码标识符、类型名、函数名、字段名、文件路径、命令、算法名保留英文。
- 同一概念只用一个中文名，并在 `Architecture/Glossary.md` 登记；其他文档只引用。
- 禁止英文句子、英文小标题、英文段落。

## 9. 结构

```text
# <标题>
<4 行文档头>

## 1. 适用范围
## 2. 规范或设计（主体，表格优先）
## 3. 实现对应（文件与函数）
## 4. 约束与失败模式
## 5. 改动影响面
## 6. 相关文档
```

`适用范围` 用两三句说明本篇负责什么、不负责什么，写成陈述句，不要写「这份文档解决什么
问题」这类元叙述。

## 10. 禁止事项

- 禁止绝对路径，例如 `D:\...`；只用仓库相对路径。
- 禁止占位符：`TODO`、`<待补充>`、`XXX`。
- 禁止跨文档复制同一段定义；需要时写一行引用。
- 禁止宣传语、开发历程叙事、口号式总结。
- 禁止把旧文档的结论当依据；以代码为准。

## 11. 篇幅

每篇有硬行数上限，包含表格、代码块与空行。上限写在业务根的 Router 里，作为该篇的
验收条件之一。

| 文档类型 | 上限 |
|---|---|
| 格式与路径规范 | 260 行 |
| 流水线、编解码内核、工程实践 | 200 行 |
| 系统与术语 | 180 行 |
| 界面设计 | 150 行 |

写长的原因通常是三类，写之前就避开：

1. 逐字段罗列能从类型定义直接看出的内容。只列取值或行为真正有差异的行。
2. 同一事实在文中出现两次以上。后出现的那个改成一句引用。
3. 整段转述源码注释，或给每个类写一段介绍。

判断标准是读者读完能否做出正确的改动决定，不是能否背下实现细节。

## 12. 完成判据

1. 文档头 4 行齐全。
2. 全文没有过去时叙述、没有变更记录、没有「未完成」类描述。
3. 关键断言有代码依据，且与代码一致。
4. 没有占位符、没有绝对路径、没有双重权威。
5. 文中引用的其他文档与代码路径全部存在。
