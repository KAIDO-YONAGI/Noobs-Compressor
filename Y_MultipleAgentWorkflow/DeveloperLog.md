# 根工作流开发日志

记录跨业务的结构变更与根索引维护。业务证据写进对应业务根的 `DeveloperLog.md`。

## 2026-10-26：工作流初始化

- 建立了根 Router、工作流指南、WorkingAgent 租约注册表与十个业务根。
- 模型入口初始未修改（`EntryMode=None`）。
- 业务根划分依据：稳定知识域，而不是源码目录形状。理由如下：
  - `Architecture`：全局结构与术语，是所有业务的共同前置知识。
  - `ArchiveFormat`：磁盘格式有独立的版本权威与最强的稳定性约束。
  - `Pipeline`：线程模型与并发组件是压缩/解压共用的运行期权威。
  - `Compression` / `Encryption`：两个算法内核的可变状态、失败模式与测试完全独立，触发词也不同。
  - `FileSystem`：路径、编码与链接的规则横跨压缩与解压两侧，且与磁盘格式解耦。
  - `GUI`：界面生命周期与线程安全有独立权威。
  - `Build`：工具链约束与测试清单独立演进。
  - `Performance`：数字与测量条件必须单点维护，否则容易出现过时数字。
  - `Security`：威胁模型需要诚实表述，不能散落在实现文档里。

## 2026-10-26：权威文档库生成

- 业务根从十个压到六个：Architecture、ArchiveFormat、Codec、Engineering、GUI、Pipeline。
  切分依据是稳定的知识域，一个业务根只拥有一篇权威文档。
- 生成六篇权威文档：每篇先由撰写 Agent 逐条核对代码后落盘，再由独立核验 Agent 与真实
  代码对抗比对，最后按核验结论定点修正。
- 每篇带硬行数上限，总量控制在源码行数的百分之十五以内。判定标准是读者读完能做出正确
  的改动决定，不是穷举实现细节。
- 接口签名以头文件为准，文档不另抄一份清单，避免与代码漂移。
- 撰写与核验规则见 `Workflow\Documentation_Standard.md`。
- `DevFiles/` 保持原样，不参与现行决策。
