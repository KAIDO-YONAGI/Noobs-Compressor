## 1. 适用范围

本篇负责构建与测试口径、性能画像、威胁模型与残余风险。压缩与加密算法原理、归档字段规范、流水线线程模型分别归 `Y_MultipleAgentWorkflow/ArchiveFormat/Router.md` 与 `Y_MultipleAgentWorkflow/Pipeline/Router.md`，本篇只写影响改动决策的结论。

## 3. 两个 CMake 文件

- `BuildTest/CMakeLists.txt` 定义 GUI 可执行目标：Qt 查找、LTO、静态与动态分支、发布选项、输出到 `bin/SFC`。静态与动态的全部差异由缓存变量 `USE_STATIC_QT` 一个开关控制。
- `BuildTest/sfc_core.cmake` 定义 21 个核心 `.cpp` 与 9 条包含目录的唯一清单，被 GUI 与测试两处 `include`。它在配置阶段逐个校验路径存在，清单写错立刻报文件级错误。

## 4. 静态与动态构建

| 维度 | `USE_STATIC_QT=ON` | `USE_STATIC_QT=OFF` |
|---|---|---|
| Qt 路径 | `CMAKE_PREFIX_PATH` 指向静态版 Qt 安装目录 | `CMAKE_PREFIX_PATH` 指向动态版 Qt 安装目录 |
| 额外系统库 | `dwmapi uxtheme imm32 oleaut32 version setupapi fontsub`，并直链 5 个静态插件 `.a` | 仅 `ws2_32 crypt32 gdi32 shell32 ole32 bcrypt` |
| 运行库 | Release 下以 `-static -static-libgcc -static-libstdc++ -s` 链接，MinGW 运行时静态化，Qt 静态链接进单个 exe | Release 下用同一组选项链接，MinGW 运行时静态化；随附 Qt DLL 与 `platforms` 插件，另复制 MinGW 运行时 DLL 供 Qt DLL 依赖 |
| 部署 | 无 Post-Build 步骤 | `windeployqt` 部署后删除网络、TLS、样式等多余文件 |

依据 `BuildTest/CMakeLists.txt:19-26`、`BuildTest/CMakeLists.txt:153-193`、`BuildTest/CMakeLists.txt:221-248`。

## 5. LTO 与归档器

LTO 由 `INTERPROCEDURAL_OPTIMIZATION` 打开，收益来自跨翻译单元内联；同一份源码在 `-O3` 下对 8 MB 不可压数据实测 301.5 → 421.5 MB/s（`BuildTest/CMakeLists.txt:104-109`）。
`CMAKE_AR` 与 `CMAKE_RANLIB` 必须换成工具链的 `gcc-ar`/`gcc-ranlib`，否则 LTO 对象只含 GIMPLE，`ar` 会报 `plugin needed to handle lto object`（`BuildTest/CMakeLists.txt:34-37`）。

`fixture_sample` 在构建目录生成样本树，`e2e_roundtrip_pack`、`e2e_roundtrip_huffman`、`e2e_roundtrip_huffman_aes` 三个用例各自压缩、解压、逐文件逐字节比对（`BuildTest/tests/CMakeLists.txt:124-139`）。

## 8. 命令

GUI 与测试是两个独立 CMake 工程，各自配置、各自构建。测试工程在配置命令里以 `-DCMAKE_CXX_COMPILER` 指定编译器；两个工程的编译器都取 Qt 自带 MinGW 11.2.0，该工具链的 `bin` 目录必须排在 `PATH` 首位，配置后按 CMake 输出的 `CXX compiler identification` 核对。`ctest` 只在 `BuildTest/tests/build` 上运行。

```powershell
cmake -S BuildTest -B BuildTest/build -DCMAKE_BUILD_TYPE=Release -DUSE_STATIC_QT=ON
cmake --build BuildTest/build --parallel
cmake -S BuildTest/tests -B BuildTest/tests/build -G "MinGW Makefiles" -DCMAKE_BUILD_TYPE=Release -DCMAKE_CXX_COMPILER=g++
cmake --build BuildTest/tests/build --parallel
ctest --test-dir BuildTest/tests/build --output-on-failure
```

## 9. 常见失败

| 现象 | 原因 | 处理 |
|---|---|---|
| `ctest` 报找不到任何测试 | 在未配置的目录上运行，或测试工程未随核心清单重配 | 先配置并构建 `BuildTest/tests/build` 再跑 ctest |
| 启动即退出、无窗口 | 动态模式缺 Qt DLL 或 `platforms` 插件 | 用 Release 加 `USE_STATIC_QT=OFF`，让 `windeployqt` 部署 |
| 配置阶段报「源文件不存在」 | 新增 `.cpp` 未收进清单 | 改 `sfc_core.cmake`，GUI 与测试同时生效 |
| 链接期 `undefined reference` | 混用了非 Qt 自带 MinGW 的目标文件或库 | 清空构建目录并重新传入 `-DCMAKE_CXX_COMPILER` 重配 |

## 10. 性能画像

端到端数字取自 13.47 GiB / 45,390 个文件的真实工程树，为 `huffman-aes` 模式、工人数取默认值 16 的完整读-算-写流水线，含磁盘 I/O；内核数字为单线程、每 8 MB 一块、重复取最快一次。两类测量不可互相换算。

测量条件见 `DevFiles/性能报告.md:22-44`：硬件为 AMD Ryzen 7 8845H，8 物理核 16 逻辑处理器；构建口径 `-O3 -DNDEBUG` 并开 LTO。数字见 `README.md:66-83`。

| 方向 | 吞吐 |
|---|---|
| 压缩 | 254.3 MiB/s |
| 解压 | 325.1 MiB/s |

这两行属版本对照批次。同规模的 16 工人 NCIEP 单独测量为压缩 304.1 MiB/s、解压 306.1 MiB/s（`DevFiles/性能报告.md:65-69`）；`huffman-aes` 的 254.3/325.1 与另一批的 275.4/345.8 是同一版本的两批读数，批间差约 8% 与 6%（`DevFiles/性能报告.md:206-208`）。

| 阶段 | 吞吐 |
|---|---|
| Huffman 编码 | 471.1 MiB/s |
| Huffman 解码 | 236.8 MiB/s |
| AES 加密 | 1261.5 MiB/s |
| AES 解密 | 1279.6 MiB/s |

每块另带 258 字节说明信息，即码长表（`CompressionModules/Huffman/Core/src/Huffman.cpp:432-447`）；压缩率最佳约 60%。

## 11. 内存峰值

峰值 ≈ `2 × (N + 2)` 个池块与 `2 × N` 个工人私有块，每块 8 MB，与输入总规模无关（`Y_Manager/CompressionLoop.cpp:45-46`, `Y_Manager/CompressionLoop.cpp:226-229`）；16 工人全量压缩实测约 500 MB（`README.md:87-88`）。

- `SFC_WORKERS` 取正整数覆盖工人数，默认取 `std::thread::hardware_concurrency()`，取不到时用 4，解压侧同口径（`Y_Manager/CompressionLoop.cpp:24-31`, `Y_Manager/DecompressionLoop.cpp:24-34`）。
- 块大小由 `Constants::BUFFER_SIZE` 定为 8 MB，改小按比例降峰值、块数同比上升，压缩与解压两侧必须同值。

## 12. 优化判据

1. 解码吞吐约为编码的一半，解压侧的优化预算先给解码器。
2. AES 吞吐约为 Huffman 编码的 2.7 倍，加密路径不值得投入优化。
3. 端到端压缩在 1 工人下 203.6 MiB/s、默认 16 工人下 304.1 MiB/s，倍率 1.49；吞吐上限由读与写决定，优化预算留给读写段（`DevFiles/性能报告.md:65-69`, `DevFiles/性能报告.md:82-86`）。

## 13. 威胁模型

保护目标为归档文件的静态内容：`.sy` 离开本机后，没有口令的一方读不出数据区与目录区。
攻击者模型是拿到归档的离线读取者，不持有口令，也不在生成归档的机器上执行代码。

| 对象 | 结论 |
|---|---|
| 数据区内容 | 保护，`HuffmanAES` 与 `AESOnly` 都加密 |
| 目录区 | AES 模式下保护，`PackOnly` 与 `HuffmanOnly` 明文 |
| 文件头与块边界 | 不保护，暴露面见第 15 节 |
| 完整性 | 不保护，后果见第 17 节 |

## 14. 密钥与完整性

口令经 SHA-256 压成 32 字节摘要，取前 16 字节作 AES-128 密钥，无盐无迭代（`EncryptionModules/Aes/src/AesFunctions.cpp:85-91`）。
每个块加密前由 `BCryptGenRandom` 生成 16 字节随机 IV 并前置写入该块，解密时从块头取回（`EncryptionModules/Aes/src/mainCircle.cpp:23-36`）。
密钥与 IV 只保证机密性：归档对篡改没有检测手段，位翻转与改写都表现为解压成功、数据错误。

## 15. 元数据暴露面

目录块在 AES 模式下由回填阶段整块原地加密，目录区之外没有额外遮蔽（`CompressorFileSystem/ArchiveFormat/src/CatalogFinalizer.cpp:40-46`）。
无论哪种模式，文件头 19 字节、块数与每块长度、归档总字节数都是明文，AES 模式下 IV 亦明文前置，据此可推断原始规模与文件数量级。

## 16. 解压侧风险

| 风险 | 机制 | 依据 |
|---|---|---|
| 路径穿越 | 归档内路径直接与解压根拼接，`..` 与绝对路径都不校验 | `Y_Manager/DecompressionLoop.cpp:156`, `CompressorFileSystem/ArchiveFormat/src/EntryParser.cpp:27` |
| 同名文件被追加 | `createFile` 检测到已存在返回 `false` 而返回值未使用，`DataExporter` 以读写方式打开文件，写入前先定位到末尾 | `Y_Manager/DecompressionLoop.cpp:313-314`, `CompressorFileSystem/DataIO/include/DataExporter.h:51-53`, `CompressorFileSystem/DataIO/src/DataExporter.cpp:19-24` |
| 链接指向归档外 | 符号链接按归档记录原样传递目标；Junction 把相对目标按链接父目录换算成绝对路径后再归一；归档记录的绝对目标直接生效 | `CompressorFileSystem/Commons/src/FileSystemUtils.cpp:453-472` |
| 链接路径已存在即中止 | 创建链接前若 `linkPath` 已存在直接抛异常，整个解压任务失败 | `CompressorFileSystem/Commons/src/FileSystemUtils.cpp:441-446` |

## 17. 残余风险

| 严重程度 | 残余风险 |
|---|---|
| 高 | 无完整性校验：位翻转或恶意改写都表现为解压成功、数据错误 |
| 高 | 密钥强度等于口令强度：单次 SHA-256 无盐无迭代，离线字典攻击成本低 |
| 中 | 密钥材料存活于进程内存：`Aes` 在析构时清零密钥与 IV；派生过程中的摘要与填充缓冲在函数内清零；口令以 `std::string` 沿调用链传递且不清零（`EncryptionModules/Aes/src/AesFunctions.cpp:80`, `EncryptionModules/Aes/src/AesFunctions.cpp:90`, `EncryptionModules/Aes/src/AesFunctions.cpp:125-129`, `CompressorFileSystem/Strategy/include/StrategyFactory.h:23`） |
| 中 | 解压无原子提交：直接写最终路径，任务失败后目标树保留已写出的部分文件 |
